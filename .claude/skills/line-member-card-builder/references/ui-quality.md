## 1. 決裁者の iPhone での確認

- 手順は**番号つき・1行1動作**。開く URL・押す所・見る所・「OK の状態」を書く。例:
  ```
  ① 日本語: <URL> を Safari で開く → 15問に答える → 一番下までスクロール
     ・「LINEで登録」の上に「今回の結果は会員証には引き継がれません…」がある
     ・「○○の相談へ」を押すと、○○のページが開く
  ② 英語: <URL>?lang=en …
  うまくいかないとき: 古い画面なら数分おいて再読み込み / 違うページならスクリーンショットを送ってください
  ```
- 本番の DB に記録が残る確認(LINE の中での操作)は、「記録が1回分残ります(実害なし)」と先に言う。
- 予行の通し確認は 6 項目程度に分けて番号で進捗を返してもらう(「1できた」「2できた」)。
- 決裁者から届いたスクリーンショットの不具合は、手元で同じ画面を再現 → 原因 → 直す → 「治った」の確認、の順。

## 2. ペルソナ実験(AI がなりきって操作)

本物の人の試験の前に、手元の使い捨て DB と本物の画面で、人物像になりきって最初から最後まで自動で操作し、各画面の写真・タップ数・小さい文字・横スクロールを記録する。

- 人物像の例(お客様): 初めてランチの会社員 / 常連の60代(小さい画面)/ SNS から来た健康志向 / 食物アレルギーがある / LINE を使わない訪日客 / 紹介された友だち / 途中でやめて再開 / 期限が近い / 空のまま押す / 同じ日に2回 / 前に撮った QR の写真 / 営業時間外 / ランクが上がる / 自分の招待リンク / とても長い名前・絵文字 / ダークモード。
- スタッフ: 新人の初日 / 混雑時に2人同時 / 店長の月末 / 本部の閲覧 / 店頭タブレットの設置と通信の不調 / 名前で検索 / 全角の数字でコード / 確認の後にお客様が取り消し。
- 結果は「見つかったこと(優先順・案つき)」と「問題なしと確かめたこと」と「限界(実際の人の迷い方は分からない)」に分けて記録し、直したあと全員をもう一度通す。数字で比べる(例: タップ数 20 → 18、注文ボタンの位置 1,348px → 777px)。

## 3. 満席の同時アクセスと外部からのアクセス

- 席数と同じ人数で、登録 → 来店 → 機能 → 会員証 → ポイント申請を同時に流す(エラー数・遅い人の時間)。警告(同じ QR の人数)が誤って出ないかもここで分かる。
- Web 版は外部からの同時アクセスも試す(ログインなし・送信なしなので、配信サイトの負荷だけ)。
- 本番には流さない。手元の DB で行い、結果の数字を記録に残す。

## 4. 最終 UI チェックの固定ページ

決裁者が「同じリンクで、内容が変わってもいつでも見られる」確認ページ。

- 撮影の道具(`tools/uicheck/capture.mjs` の型): 本物の画面+使い捨て DB+擬似の LIFF で、お客様の画面を全部の言語で、スタッフ画面を権限ごとに撮る(iPhone 相当の幅 390px・縦長の全体)。撮影中のエラー数を出す。
- ページ作り(`build.mjs` の型): 画面のグループごとに、言語を横に並べる。版(コミット)と撮影時刻を入れる。
- 公開は Artifact などの**同じ URL に上書き**で(新しいリンクを増やさない)。撮り直しは1コマンド(スクリプト)にしておく。
- 変更を公開したら撮り直して更新し、決裁者には「いつものリンクで更新済み」と言う。
- 撮った写真は自分の目でも見る(数値に出ない文字切れ・重なり)。

## 5. 外部レビュー(Codex など)の依頼一式

決裁者が別の AI に最終チェックを頼むときに渡す一式(`review_pack.mjs` の型):

| ファイル | 中身 |
|---|---|
| `AGENTS.md` | その AI が最初に読む指示: 役割・**ファイルを変えない・外部に送らない**・日本語で・事実と推測を分ける・指摘には画面番号かファイルと行を付ける・フォルダの中身・進め方 |
| `01_依頼文.md` | 背景・使う人と場面(表)・見てほしい観点(統一感・見やすさ・わかりやすさ・直感的に使えるか)・実装の面で見てほしいこと・見なくてよいこと・出力の形(総評3行・指摘の表(重要度・画面・観点・指摘・理由・修正案)・良い点・決定事項への意見・確かめきれなかったこと)・30件以内 |
| `02_画面集.pdf` | 全画面。表紙に番号つきの目次。お客様の画面は言語を横に並べる |
| `03_決定事項と前提.md` | 変えない前提(言葉づかいのきまり・言語の範囲・ログインの理由・見た目の承認済みの所・既知の保留)。反対意見は「決定事項への意見」として分けてもらう |
| `shots/` | 1枚ずつ(番号_画面_言語.jpg) |
| `src/` | 画面と部品のソース(テスト・設定・画像は除く)。秘密らしい文字列があれば作るのを止める |

- 決裁者が使う道具に合わせる(例: Codex のデスクトップアプリなら `AGENTS.md`)。zip にして渡す。
- 返ってきた指摘は1件ずつ**本当にそうか確かめてから**直す(コードで再現する)。決裁者の判断が要るもの(例: リンク先・機能を足すか)は、メリット・デメリットの表にして選んでもらう。
- 直したら「指摘 → 直した所 → テスト」の対応を記録に残す。

## 6. 表現チェックと翻訳確認

- グループの表現チェックの部署に出す依頼書(Google ドキュメント)に、お客様に見せる文を**番号つきで**足していく(日本語+英語+中国語)。新しく足した文だけを伝えれば済むようにする。
- 翻訳の確認表(スプレッドシート): 画面・場所・日本語・英語・中国語・確認者の欄。
- 両方とも「確認済み」になるまでは、画面の文は「案」。決裁者が確認済みと言ったら、日付つきで記録する。

## 7. よく直した所(チェックリスト)

- [ ] 押せる所は 44px 以上(言語の切り替えボタンも)
- [ ] 文字は 13px 以上。補助の文字の色はコントラスト比 4.5 以上(例 `#6f685e`)
- [ ] 読み込み中・通信失敗・時間切れ・「結果が分からない」の表示がある(とくにお金にあたる操作)
- [ ] 失敗したときの文が「次にすること」を言っている(「電波の良い場所で、もう一度」)
- [ ] 送れなかったのに「送った」と言っていない(パスワード再設定など)
- [ ] 1回目の人に、同じ内容を2回出していない
- [ ] 見出しとボタンが同じ文で重なっていない
- [ ] グラフの点数の意味・専門用語(五行など)の説明が、開けば読める
- [ ] 翻訳の漏れ(英語・中国語の画面に日本語が残っていない)。括弧と記号が言語ごと
- [ ] 画面を切り替えたらフォーカスが見出しへ。読み上げのラベル
- [ ] スタッフ画面: 確定の前に誰の何 pt かが大きく見える。確定のあとはコードの欄を空に。タブを素早く切り替えても前のタブの結果が出ない
- [ ] 店頭 QR: 横向きの小さいタブレットでも1画面に収まる
- [ ] 表が横に長いときは「横にスクロールできます」の案内
