# 完成形の構成(10ZEN の会員証フェーズ1を例に)

別の店で作るときも、この形を出発点にする。名前・数字は例。

## 1. 構成要素

| 層 | 使うもの | 理由 |
|---|---|---|
| お客様の入口 | LINE の LIFF(LINE の中で開く Web 画面) | 友だち追加済みのお客様がアプリなしで開ける。LINE の ID トークンで本人確認できる |
| 画面 | 静的な HTML+ES モジュール(ビルドなし・npm の依存なし) | 公開サイト(GitHub Pages など)に置くだけ。秘密を置かない |
| サーバー | Supabase(PostgreSQL+Auth+Edge Functions) | 権限チェック付きの関数(RPC)で守れる。スタッフのログインに Auth |
| 旧システムとの橋 | 旧システム(例: GAS とスプレッドシート)の停止部品・同期 | 切り替えの日に書き込みを止め、要約を2回取って一致を確かめる |
| 運用 | GAS の毎日のバックアップ+別アカウントの見張り役+月次レポート | 止まったらメールで気づける |
| 外部サービス | 注文(例: ダイニー)・POS(レジの CSV) | 自作しないものは連携だけ。ID は設定に持ち、空なら機能を出さない |

**自作するか外部に任せるか**は、導入予定のサービスに「ポイントは再現できるか・CSV を出せるか・リッチメニューに自前の画面を置けるか」を聞いてから決める(10ZEN: 会員証・ポイント・ランクは自作、配信と注文は外部)。

## 2. データ(DB)

**基盤(100番台の最初)**
| 表 | 中身 | 決まりごと |
|---|---|---|
| `app_settings` | 制度の値(使用単位・有効時間・受付時間・同時来店の警告人数など) | 値の変更は行の更新だけで済む。変更は監査ログへ |
| `point_rules` | 登録・来店・紹介・キャンペーンのポイント(期間つき) | キャンペーンは開始日・終了日で |
| `rank_thresholds` | ランクの基準(累計ポイント) | ランクは下がらない。累計は使っても減らない |
| `system_state` | 運用の状態(1行) | 4章 |
| `test_allowlist` | 試験に参加できる LINE の ID | `test` のときだけ効く |
| `policy_decisions` | 未決定の制度(使用単位・紹介・移行の範囲など) | **全部決まるまで `open` にできない** |
| `members` / `member_identities` | 会員(番号・ランク・残高のキャッシュ・状態)/ 外部 ID(provider・issuer・subject) | 将来ほかの事業(物販・スクール・EC)とつなぐ口を最初から持つ |
| `point_ledger` | ポイントの台帳 | **追記専用**(トリガーで更新・削除を拒否)。取引ごとの冪等キー |
| `visits` | 来店(1会員1日1行) | 日付は日本時間 |
| `redeem_requests` | ポイント使用の申請(6桁のコード・3分有効) | スタッフが確定して初めて減る |
| `staff_users` | スタッフの権限 | 3章 |
| `audit_log` | 誰が・何を・誰に | 一覧で誰の情報を見せたかまで残す |
| `api_throttle` | 回数制限 | 総当たり対策 |
| `backup_runs` | バックアップの記録 | 見張り役が読む |

**機能ごとに足した表(102〜)**: 特典チケット(種類・1枚1行・使用申請)、体質チェック(同意・結果・案内のクリック)、KPI(本番開始日・目標・レジの日別/月の客数)、友だち紹介(招待コード・紹介の記録)。どれも「試験」の印(`is_test`)を持ち、本番の集計に混ぜない。

**関数の名前の付け方**
- `app_*`: お客様(検証済みの issuer/subject を Edge Function から受け取る)
- `staff_*`: スタッフ以上 / `manager_*`: 店長だけ
- `_*`: 内部用(外から呼べない)
- 運用: `set_system_state`・`decide_policy`・`allow_test_identity`・`reconcile_balances`・`verify_balances`・`cutover_report`・`export_backup`・`restore_backup`・`import_opening_balance`

## 3. 権限

| 役割 | できること | できないこと |
|---|---|---|
| 店長 manager | すべて(手動のポイント調整・取り消し・目標と KPI・CSV 出力・設定の切り替え) | — |
| スタッフ staff | ポイント使用とチケットの確定・会員の一覧と詳細・集計・体質の集計 | 手動調整・KPI(部品を DOM に出さない) |
| 閲覧 viewer(本部) | 集計と KPI を見るだけ | 個人の健康に近い情報・変更すべて |
| 店頭 kiosk | 来店 QR を受け取るだけ | 会員の情報・スタッフの操作すべて |

スタッフも自分のスマホでログインする前提にする(片手・混雑時)。

## 4. 運用の状態(frozen / test / open)

- `frozen`(既定): お客様の書き込みを全部止める。取り込み・照合・切り戻しのとき。
- `test`: `test_allowlist` の LINE の ID だけが、本番と別の名前空間(issuer に `test:` を付ける)・試験の会員番号(T…)で使える。旧システムへの反映は止まる。**本番の DB で予行ができる。**
- `open`: 本番。試験の会員には誰も到達できない。
- `test → open` は直接行けない。`frozen` を通り、残高の照合が一致し(`reconciled`)、方針が全部決まり、旧システムを止めた確認(`legacy_writes_stopped`)を添えたときだけ進む。

## 5. API(Edge Function)

**member-api(お客様。POST・1つの関数)**
- 認証: ヘッダーの LIFF の ID トークンを LINE の検証 API で確かめ、検証済みの `sub` だけを使う。クライアントが送る LINE の ID は信用しない。
- 操作: `me`・`register`・`checkin`・`redeem_request`・`redeem_cancel`・`ticket_request`・`ticket_cancel`・`constitution_submit`・`invite_seen`・`referral_click` など。
- 応答に外部 ID・内部 ID を入れない。本文の上限(例 4KB)。CORS は画面の配信元だけ。

**店頭 QR(staff-qr と member-api で同じ `qr.ts`)**
- QR に載せるのは「30秒ごとのスロット番号+署名」だけ(個人情報なし)。署名鍵は既存の秘密から用途ラベルつきで派生させ、秘密を増やさない。
- 有効なのは「今のスロットから数個前〜1個先」。写真を店外に送っても数分で無効。
- 同じスロットで記録した人数が設定値以上なら、スタッフ画面に「要確認」(満席の団体を誤検知しない値にする。10ZEN は 42 席で 6 → 15 に上げた)。

**backup-export**: バックアップの書き出しと月次レポート用の集計。用途ごとのトークン(HMAC で派生)で呼ぶ。

**関数の公開**: 取り込むライブラリは版を固定する(例 `npm:@supabase/supabase-js@2.45.4`)。「最新版」を取りに行くと、ある日突然組み立てに失敗する。

## 6. 画面

| 画面 | 使う人 | 中身 |
|---|---|---|
| `card.html` 会員証 | お客様(LINE) | 登録・カード(表: ランクの色・会員番号・ポイント / 裏: 店の情報・予約)・来店のお知らせ・ポイントを使う(6桁のコード)・特典チケット・友だち招待・ランク特典・店独自の機能の入口・言語の切り替え |
| `check.html` 店独自の機能(例: 1分体質チェック) | お客様(LINE) | 同意 → 1問1画面 → 結果(グラフ・おすすめ・案内・診断ではない旨)。途中から再開 |
| `web-check.html` Web 版 | LINE を使わない人・来店前の人 | ログインなし・何も送らない。結果の下に LINE 登録の案内 |
| `qr.html` 店頭 QR | 店頭タブレット(お客様が見る) | 30秒ごとの QR・会員の特典と使い方。**操作できる部品を置かない**。言語は自動で切り替え |
| `staff.html` スタッフ画面 | スタッフ・店長・本部 | ポイント使用の確定(最上段)・会員・集計・体質の集計・目標と KPI・CSV(店長) |
| `table-qr.html` お席の QR カードの印刷 | 店長 | テーブルごとの QR(機能 → そのまま注文) |
| `reset.html` パスワード再設定 | スタッフ・店頭タブレット | メール → 新しいパスワード(登録の有無は画面に出さない) |

**見た目の決まり(10ZEN の例)**: 会員証は和紙色の地・明朝体の見出し・生薬の水彩イラスト・ランクごとの枠の色。スタッフ画面は白地+機能ごとの色。押せる所は 44px 以上。文字は 13px 以上・濃さはコントラスト比を確かめる。

**画面の作り**: 見た目に依存しない部品(`app-core/*.mjs`: クライアント・画面の状態・文言・判定・多言語)と、見た目(`app-reference/*.html`)を分ける。最終の見た目を差し替えても部品とテストは残る。

## 7. 設定値の例(10ZEN)

| 値 | 例 | メモ |
|---|---|---|
| 登録 / 来店 | 100pt / 100pt(1日1回) | 登録した日を来店に数えるかは方針で決める |
| ポイントの価値 | 100pt = 10円、使用は 100pt 単位 | |
| 使用コードの有効時間 | 180秒 | |
| 来店の受付時間 | 11〜21時(運営変更の後 22時) | 時間外は「対象外」と出るのは仕様 |
| ランク | 0 / 1,000 / 3,000 / 6,000 / 10,000pt | 来店回数の目安を添えて決めてもらう |
| 同じ QR の警告 | 15人 | 席数から決める |
| 紹介 | 暦月5人まで・特典は友だちの初来店のとき | 自己紹介・二重付与を DB で防ぐ |

## 8. ファイルの置き方

```
phase1-app/
  db/NNN_名前.sql と NNN_名前_DOWN.sql   … 番号順。必ず戻しと対
  functions/<関数>/handler.ts, index.ts    … 中身(handler)とつなぎ(index)を分け、handler をテストする
  app-core/*.mjs                           … 部品(テストは test*.mjs)
  app-reference/*.html, assets/, vendor/   … 画面(vendor は同梱するライブラリ)
  gas_backup/ gas_freeze/ gas_sync/        … 旧システム側の部品
  patches/                                 … テスト用の部品(使い捨て PostgreSQL、JWT/LINE のスタブ)
  tools/build_v2.mjs                       … 公開用の一式を組み立てる(秘密が混ざっていたら止まる)
  tools/uicheck/                           … 画面の撮影・確認ページ・外部レビューの資料
  run_tests.sh                             … 全部のテスト(期待件数つき)
  <機能>_DESIGN_<日付>.md など              … 設計書・監査・手順書・記録
v3/                                        … 公開サイトに置く組み立て済みの一式(main ブランチ)
```

## 9. テスト

- **DB**: 使い捨ての PostgreSQL を起動し、全部の SQL を入れて、関数を権限ごとに呼ぶ。攻撃(他人のチケット・権限の越権・二重使用・同時登録のすり抜け)を実際に試す。
- **関数**: LINE と JWT のスタブで handler を呼ぶ。
- **部品**: 判定・文言・多言語(項目がそろう・禁止語がない・中国語にかなが混ざらない)。
- **実ブラウザの通し(e2e)**: Playwright で、擬似の LIFF とローカル DB につないで、登録 → 来店 → 機能 → ポイント使用 → スタッフの確定まで。
- `run_tests.sh` は**スイートごとに期待件数**を持ち、件数が減っても失敗にする(テストを黙って消せない)。10ZEN は最終で 311 件。
- 本番には接続しない。秘密が要るスイートだけ SKIP を許す。

## 10. 運用の仕組み

- **毎日のバックアップ**(深夜): DB の書き出しをドライブに保存し、成功を `backup_runs` に記録。
- **見張り役**(別の Google アカウント・毎朝): 24時間以内の成功がなければメール。自分から自分へのメールは見落とすので、件名でスター・ラベルを付けるフィルタを作る。
- **月次レポート**(毎月1日): 前の月の集計だけ(個人情報なし)。本番開始日の前は送らない。
- **復元の訓練**: 古い形のバックアップを新しい DB に戻せるか、テストで確かめる(監査で見つかった実例あり)。
