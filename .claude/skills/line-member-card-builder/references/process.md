# 段階ごとの中身と成果物の型

## 目次
- 段階0 現状を知る
- 段階1 基盤
- 段階2 監査
- 段階3 見た目
- 段階4 機能を足す
- 段階5〜6 予行と人での試験(詳しくは production-ops.md・ui-quality.md)
- 段階7 仕上げ
- 段階8 切り替え
- 資料の型(設計書・実装メモ・監査の依頼・監査報告・引き継ぎメモ・実施記録)

## 段階0 現状を知る

- 旧システムの制度の値(登録・来店・使用・ランク・キャンペーン・紹介)を**読み取りで**集め、`app_settings`・`point_rules` の初期値にする。分からない値は `policy_decisions` に「未決定」として入れ、決まるまで本番にしない。
- 旧システムの店頭の QR・リッチメニュー・管理ページの場所を控える(切り替えの日に撤去・差し替える)。
- 導入予定の外部サービスへ聞くこと: ポイント・ランクを再現できるか / 会員と来店の CSV を出せるか / リッチメニューに自前の画面を置けるか / 注文画面の URL の形。
- 社外秘の文脈(数字・決定・関係者)は非公開の文書を正本にする。リポジトリが公開なら写さない。

## 段階1 基盤

- 最初から入れるもの: 追記専用の台帳・冪等キー・行ロック・運用の状態・試験の分離・方針のゲート・権限つきの関数・監査ログ・回数制限・バックアップと復元・切り替えの部品(取り込み・照合・報告)。後から足すと既存のデータを直すことになる。
- 本番には入れない。使い捨て DB のテストで固めてから、段階5で入れる。
- 画面は最小(参照実装)。見た目に依存しない部品を先に作る。

## 段階2 監査

- **実装したのとは別のセッション・別の AI** に、読み取りだけで頼む。本番に接続しない。使い捨て DB で攻撃を実際に試してもらう。
- 依頼には範囲(コミットの差分)・やり方・見てほしい観点・出力の形(重大度 高/中/低/情報、結論、確認できたこと、確認できなかったこと、本番の前に必要な手順)を書く。
- 指摘は1件ずつ直してコミットを分け、報告書に「指摘への対応」を追記する。直さないものは理由と、決裁者の決定を書く。
- 10ZEN の実例: バックアップが新しい DB に戻せない(中)・停止中の会員のチケットを確定できる・設定の切り替えが凍結中も動く・スタッフが一覧で個人の結果をまとめて見られる(決裁者が「見せる」と決め、誰を見たかを記録)。

## 段階3 見た目

- スタッフ画面はスキル `store-dashboard-builder` の手順。
- 会員証は、店の既存の紙のカード・ショップカードの絵柄を表に使い、ランクの色を枠に。素材(イラスト)は高解像度・小さく上品に。決裁者が細かく直したがる所なので、**固定 URL のプレビュー**で何度でも見られるようにする。
- 表裏のあるカードは iPhone の LINE で表裏が重なることがある(裏返った面を `visibility: hidden` で隠す)。

## 段階4 機能を足す

SKILL.md の「1機能を足すときの最小の型」のとおり。機能ごとに設計書を作り、決裁者に1問ずつ決めてもらう。途中で方針が変わったら(例: 今日の体調3問 → 毎回の任意のチェック)、設計書に新しい章を足し、古い章の先頭に「〇章が優先」と書く。

## 段階7 仕上げ

`references/ui-quality.md`。多言語 → 最終 UI チェックの固定ページ → 外部レビュー → 表現チェック・翻訳確認。

## 段階8 切り替え

`references/production-ops.md` の「切り替え手順書」。

## 資料の型

### 設計書 `<機能>_DESIGN_<YYYYMMDD>.md`
```
# <機能>の設計(日付)
- 決定者・決め方(例: テキストで1問ずつ)
- 状態(設計確定 / 実装済み・本番未適用 / 本番適用済み)
- 公開リポジトリのため入れないもの
## 1. ねらい
## 2. 決めたこと(表。選ばなかった案と理由も短く)
## 3. 画面
## 4. データ・保存するもの・同意
## 5. 権限
## 6. 言葉づかい
## 7. 公開前に確かめること(誰に)
## 8. 実装メモ(作ったあとに追記)
## 追補(日付): 変更の決定
```

### 実装メモ(設計書の中)
作った物(DB の番号・関数名・表)/ 画面の要素 ID / 設計書に書いていなかった細かい決め方 / 差し替える文とデータの場所 / テスト(件数)/ まだのもの・確かめたいこと。

### 監査の依頼
```
対象: ブランチ <名前> の <コミット>。基準は <コミット>(git diff A..B -- <ディレクトリ>)
範囲: DB <番号>〜<番号> と戻し、関数、画面、部品
やり方: 読み取りだけ。本番に接続しない。使い捨ての PostgreSQL で攻撃や誤操作を実際に試す。アプリのコードは変えない
観点: お客様が他人の物を操作できないか / 権限の越権 / 二重使用・二重付与 / 同時実行 / 試験と本番の混ざり / 凍結中に動く物 / バックアップと復元 / 適用の順番
出力: 結論 → 指摘(高・中・低・情報。再現手順と直し方の案)→ 確認できたこと → 確認できなかったこと → 本番の前に必要な手順
```

### 引き継ぎメモ `HANDOFF_<日付>.md`
先頭に「現在地(新しいセッションはここから読む)」: 本番の状態・済んだこと・**決裁者待ちの作業**・その後の予定・注意(触ってはいけない ID など)。続けて、終わったこと・わかったこと・判断待ち・方向の決定(日付つき)。

### 実施記録(予行の手順書の最後の章)
1行ずつ: 日時・承認の言葉(例「承認(2人とも)」)・したこと・確かめた結果(数字)・戻すもの(戻す予定の日時)・戻した記録。
