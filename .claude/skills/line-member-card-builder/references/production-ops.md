# 本番に触れる作業(承認・適用・公開・予行・切り替え・戻し方)

## 目次
1. 承認の取り方
2. 本番の状態を読み取りで確かめる
3. DB の変更を安全に入れる(固定コミット+md5+指紋)
4. Edge Function の公開
5. 画面の公開(組み立て → 公開サイト)
6. 設定値の変更・一時的な変更
7. 試験の会員のリセット
8. 本番予行(test のまま)の手順書
9. 切り替え手順書

## 1. 承認の取り方

本番の DB・関数・公開サイト・設定・アカウントを変える前に、決裁者に次を短く示して「承認」をもらう。

```
何を: DB 114(同じ QR で「要確認」を出す人数を 6 → 15)
なぜ: 42人同時の試験で、満席の団体が誤って警告された
影響: お客様の画面は変わらない。スタッフ画面の警告だけ
戻し方: 114_DOWN を流す(数秒)
確かめ方: 適用前後の指紋が手元と一致すること
```

- 承認は1件ごと。「さっき承認したから」で次の作業に広げない。
- アカウントを作るときは、メールアドレスだけ教えてもらい、パスワードは本人が設定する(聞かない)。DB 側で役割だけ付ける。
- 本人が自分で SQL を流したほうが早い場面(パスワードを忘れた等)は、**何をする SQL か・どこに貼るか**を画面の場所つきで渡す。

## 2. 本番の状態を読み取りで確かめる

作業の前後に、読み取りだけで: 適用済みの DB の番号(`supabase_migrations.schema_migrations` の最後)・運用の状態・設定値・会員数(本番/試験)・残高と台帳の一致(`verify_balances()`)・直近のバックアップの成功。

## 3. DB の変更を安全に入れる

**なぜこの方式か**: 大きな SQL(数十 KB)を管理ツール経由で送ると、通信が途中で切れる(10ZEN では 60 秒で切れ、3回とも失敗)。そこで DB 自身にファイルを取得させ、中身と結果を確かめてから確定する。

**前提**: 公開リポジトリ(または DB から読める場所)に SQL がコミット済み。DB に `pg_net` がある。

**手順**(`scripts/make_apply_sql.mjs`)
1. 手元の使い捨て DB に、本番と同じ番号まで入れて、指紋を取る:
   `node scripts/make_apply_sql.mjs fp-query [--functions …] [--tables …] [--exclude-tables 旧システムの表]`
   を手元と本番の両方で流し、**適用前の指紋が一致する**ことを確かめる(一致しなければ止める。本番がどこかで手で変えられている)。
2. 手元で新しいファイルを入れたあとの指紋を控える(これが「期待する指紋」)。
3. 本番で取得: `node scripts/make_apply_sql.mjs fetch --url https://raw.githubusercontent.com/<owner>/<repo>/<コミットのハッシュ>/<path>.sql` が出す SQL を流し、`net._http_response` の id を控える。**ブランチ名ではなくコミットのハッシュ**(後で中身が変わらない)。
4. 適用: `node scripts/make_apply_sql.mjs apply --file <path>.sql --resp-id <id> --fp <期待する指紋> --version <14桁> --name <名前>` が出す SQL を流す。中で「md5 の一致 → 実行 → 指紋の一致 → 履歴に記録」を1つの取引で行い、どれかが違えば全部取り消される。
5. 適用後にもう一度 `fp-query` を流して一致を確かめ、予行の実施記録に「固定コミット・md5・前後の指紋」を書く。

**手元で先に通しの予行をする**: 使い捨て DB に `net._http_response` と `supabase_migrations.schema_migrations` の表を作って同じ SQL を流し、わざと違う指紋で失敗(取り消し)することも確かめる。

**ほかに気をつけること**
- Supabase の API 経由では、WHERE のない UPDATE/DELETE が安全装置(pg_safeupdate)で拒否される。1行だけの設定の表でも `where id` を付ける。手元の DB には安全装置がないので、関数の中に WHERE のない UPDATE/DELETE が無いことをテストで見張る。
- 複数の文を一度に送ると(一時表+begin/commit など)時間切れになることがある。1つの文(CTE)にまとめる。
- 既存の関数は署名と権限を変えずに置き換える。新しい関数には権限を明示する(既定の権限に頼らない)。
- 新しい API(関数)を DB より先に公開すると失敗する組み合わせがある。順番を手順書に書く。

## 4. Edge Function の公開

- 公開の前に、今の本番の中身が git のどのコミットと同じかを確かめる(戻すときの版)。
- 取り込むライブラリは版を固定する。
- 公開した中身が手元のファイルと1文字単位で一致することを確かめ、鍵なしの呼び出しが 401 で拒否される(正常に起動している)ことを見る。

## 5. 画面の公開

- 組み立ての道具(`tools/build_v2.mjs` の型)で、LIFF ID と**公開キーだけ**を入れた一式を作る。秘密らしい文字列があれば止まる。ファイル一覧と SHA-256 を MANIFEST に書く。
- 公開サイトの別の場所(例 `/v3/`)に置き、古い版(`/v2/`・トップ)は変えない。試験用の LIFF の開き先だけを新しい版に向ける。
- 手順: 公開ブランチ(main)の作業用コピー(git worktree)を作る → 組み立てを新しいフォルダに出す → 古いフォルダと入れ替える → 変わったファイルを確かめる(`git status`)→ コミット → push → 作業用コピーを消す。
- 公開サイトの反映には数分かかる。決裁者に「古い画面が出たら数分おいて再読み込み」と添える。
- 公開したら、確認用の固定ページ(ui-quality.md)も撮り直す。

## 6. 設定値の変更・一時的な変更

- 設定の変更は監査ログに残る関数で行う。
- 一時的な変更(例: 夜に試すため受付を 0〜24時)は、承認のときに**戻す日時**を決め、実施記録に「戻す予定」→「戻した(時刻)」を書く。本番開始の前に元の値であることを必ず確かめる。

## 7. 試験の会員のリセット

決裁者が「一から試したい」とき(承認が要る):
- 会員を停止(closed)にし、LINE との紐づけ(`member_identities`)を外す。**台帳は消さない**(追記専用)。残高と台帳の一致を確かめる。
- 監査ログに `test_member_reset` を残す。`test_allowlist` はそのまま(同じ LINE で登録し直せる)。次の会員番号は続きから。

## 8. 本番予行(test のまま)の手順書

```
# 本番での予行演習の手順書(日付・承認待ち)
## 1. 今の本番の状態(読み取りで確認)
## 2. 変わること・変わらないこと(お客様には影響なし、など)
## 3. 先に決めていただくこと(3つまで)
## 4. 手順(私が行う作業・所要時間)
## 5. iPhone で確かめること(番号つき。会員証 → 来店 → 機能 → スタッフ画面 → 特典 → 紹介)
## 6. 元に戻す方法
## 7. 気をつけること
## 8. 承認していただくこと
## 9. 実施記録(承認の言葉・結果・途中で起きたことと対処)
```
- 予行は `test` の状態で、`test_allowlist` に入れた LINE の ID だけ。紹介を試すときは相手の ID も入れる。
- 翌朝、夜中のバックアップと見張り役が正常かを確かめて、予行の完了とする。

## 9. 切り替え手順書

```
# 切り替え手順書(案。本番開始は別の承認)
## 1. 先に決めること(表: 旧会員のポイントを引き継ぐか / 本番の LIFF / 本番開始日 / …。状態と決定日)
## 2. 前日までにやること
## 3. 当日の順番(表: 作業・誰が・確かめること)
## 4. 旧会員の引き継ぎ(引き継ぐと決めた場合だけ)
## 5. 本番開始の直後に確かめること
## 6. 本番開始の後でやること(当日〜1週間)
## 7. 試験のデータの扱い
## 8. 戻し方
```

**前日までの例(10ZEN で実際に出てきたもの)**
- バックアップの成功を確かめる。
- 本番の LIFF ID で画面を組み立てて公開。店頭 QR の関数の設定(LIFF の URL)・関数の許可する配信元。
- LINE Developers: shareTargetPicker をオン・リッチメニューのリンク先。
- Supabase の Site URL と Redirect URLs(パスワード再設定のメールのリンクが開けるように。既定は localhost のまま)。
- 独自のメールの送信元(SMTP)。標準の送信はプロジェクトのメンバーにしか届かない。
- 旧システムの店頭 QR の撤去場所を確認(旧 QR を読むと旧システムが開いてエラーになる)。
- 店頭タブレットの準備: 通常のブラウザでログイン(プライベートブラウズ不可)→ ホーム画面に追加 → 自動ロックなし・画面の固定 → 履歴を消さない。
- 登録ポイントの案内とキャンペーンが重なっていないか。

**当日の順番の例**: 手動バックアップ → 旧システムの書き込みを止める(未処理なし・要約を2回取って一致)→ 新しい仕組みを `frozen` → 設定の変更と本番開始日 → 残高の照合(一致)→ LIFF の開き先を切り替え・店頭タブレットを開き直す → `open`(旧システムを止めた確認を添える)→ 動作確認。

**本番開始の後**: レジの客数の取り込みをやり直す(試験の分は使われない)・月次レポートの設定・注文サービスの ID を設定・お席の QR を本番の LIFF で作って印刷・バックアップの保存先を店のアカウントへ(見張り役は別のまま)。

## 10. 戻し方

| いつ | 戻し方 |
|---|---|
| DB の変更のあと(本番開始前) | `_DOWN.sql` を新しい番号から順に流す(バックアップからの復元より確実。古いバックアップは新しい DB に戻せないことがある) |
| 本番開始の前 | 新しい仕組みは `frozen` か `test` のまま。旧システムを再開(本番開始を一度もしていない場合だけ)。LIFF の開き先を戻す |
| 本番開始の後 | `frozen` で止める(お客様には「メンテナンス中」)。`cutover_report()` で開始後の動きを見て、直して再開するか決める。旧システムには戻さない(開始後のポイントが旧システムに無い) |
