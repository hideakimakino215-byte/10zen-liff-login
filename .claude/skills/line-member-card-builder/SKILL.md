# LINE デジタル会員証の作り方

非エンジニアの意思決定者(店の事業責任者など)が、**iPhone で見て、言葉で決めて、承認したものだけが本番に入る**状態で、紙や古い仕組みの会員制度を LINE の会員証に置き換える。速さより「お客様のポイントを壊さない」「決めたことを守る」「確かめたことだけを確かめたと言う」を優先する。

このスキルは、10ZEN(東京・青山の薬膳レストラン、42席)で 2026-10 に作った会員証を手本にしている。数字や名前は例で、別の店でも同じ型で作れる。

## 完成形のひとこと

```
お客様(LINE)── LIFF ─→ 会員証 card.html ─┬→ 体質チェックなど店独自の機能 check.html
                                           └→ 友だち招待(shareTargetPicker)
お客様(LINE なし)────→ Web 版 web-check.html(ログインなし・何も送らない)
店頭タブレット(ログイン1回)→ qr.html: 30秒ごとに変わる来店 QR
スタッフのスマホ・レジ横 ──→ staff.html: ポイント使用の確定・会員・集計・目標と KPI
            ↓ すべて
   Edge Function(member-api: LINE の ID トークンを検証 / staff-qr / backup-export)
            ↓
   PostgreSQL(Supabase): 表に直接触らせず、権限チェック付きの関数(RPC)だけ
   ・ポイントは追記専用の台帳(書き換え・削除不可)  ・運用の状態 frozen / test / open
   ・監査ログ  ・毎日のバックアップ → 止まったらメールする見張り役(別アカウント)
画面は静的ファイル(GitHub Pages など)。秘密は置かない(公開キーだけ)
```

詳しくは `references/architecture.md`。

## 進め方の全体(段階と成果物)

| 段階 | やること | 決裁者に見せるもの |
|---|---|---|
| 0. 現状を知る | 旧システム(紙・GAS・外部サービス)の制度の値を読み取りで集める。導入予定の外部サービス(POS・注文)との役割分担を決める | 「今の制度の値」と「自作する/しない」の表 |
| 1. 基盤 | DB(台帳・状態・権限・監査・バックアップ)と API と最小の画面。**本番に入れず**、使い捨て DB のテストで固める | テスト件数と「本番には未反映」 |
| 2. 監査 | 別のセッション・別の AI に、読み取りだけの独立監査を頼む。指摘を直す | 監査の結論(高・中・低の件数)と対応表 |
| 3. 見た目 | 会員証・スタッフ画面・店頭 QR を作り、擬似データのプレビューを iPhone で見てもらう | 固定 URL のプレビュー |
| 4. 機能を足す | 1機能ずつ「設計書 → 決裁 → DB(番号つき+戻し)→ 部品 → 画面 → テスト → 実装メモ」 | 設計書(決めることを1問ずつ) |
| 5. 本番予行 | 本番の DB に `test` の状態で入れ、許可した LINE の ID だけで通しで試す | 予行の手順書 → 承認 → 実施記録 |
| 6. 人で試す | 決裁者の iPhone で通し。AI のなりきり試験(ペルソナ)。満席の同時アクセス | 確認の手順(番号つき)と結果 |
| 7. 仕上げ | 多言語・最終 UI チェックの固定ページ・外部レビュー(Codex など)・表現チェック・翻訳確認 | 指摘の表と、決めてもらう選択肢 |
| 8. 切り替え | 切り替え手順書(先に決めること・前日・当日の順番・戻し方)。**本番開始は別の承認** | 手順書と承認 |

各段階の中身・テンプレートは `references/process.md`。

## 守ること(理由つき)

**お客様のお金にあたるもの**
- ポイントは**追記専用の台帳**。残高は台帳の合計と照合できるキャッシュにする。後から「どこで増えた・減ったか」を必ず説明できるようにするため。試験の記録も消さずに「試験」の印で分ける。
- 付与・使用・来店・登録は**冪等**(同じ取引を2回送っても1回)にし、残高は会員の行のロックで順番に処理する。LINE のアプリは通信が切れやすく、二重送信が普通に起きる。
- 来店ポイントは**店にいる人だけ**が取れるようにする: 30秒ごとに変わる QR・受付時間(例 11〜21時)・1日1回・同じ QR で多数が記録したら「要確認」。QR 画面のログインを外すと自宅から取れてしまう。

**権限と個人情報**
- 表への直接アクセスは誰にも与えず、関数ごとに権限を確かめる。画面で隠すのは補助で、権限のない部品は **DOM ごと出さない**。
- 閲覧(本部)には個人の健康に近い情報(体質の結果など)を返さない。グループ会社への共有は**集計だけ**。個人の結果は、お客様が自分の画面を見せる形にする。
- 描画は `textContent` だけ。外部の CDN・解析タグを入れない(LIFF の SDK だけは LINE の配信元から)。

**本番**
- 本番の DB・関数・公開サイト・設定(受付時間など)を変える前に、**何を・なぜ・どう戻すかを示して承認をもらう**。承認は1件ごと。前の承認を次の作業に流用しない。
- 運用の状態を3つ持つ: `frozen`(すべての書き込みを止める)・`test`(許可した LINE の ID だけが、本番と分けた試験の会員で使える)・`open`(本番)。`test` から `open` へは必ず `frozen` を通り、旧システムを止めたことの確認を添えないと進めない。
- 一時的な変更(例: 夜の試験のための24時間受付)は、**戻す時刻を決めて記録し、戻したら記録する**。

**リポジトリと資料**
- リポジトリが公開なら、教材・社内資料・原価や売上・個人情報・秘密(鍵・パスワード・PIN)を絶対に入れない。社外秘の文脈は非公開の文書(Google ドキュメントなど)を正本にして、コネクタで読む。
- 決裁者にパスワードを聞かない。アカウントはメールアドレスだけ教えてもらい、パスワードは本人が設定する。

**言葉づかい(飲食・健康まわり)**
- 医薬品の広告の決まりに合わせ、「治る・効く・改善」を使わない(英語の cure / treat / heal / improve / effective、中国語の 治疗 / 治愈 / 疗效 / 改善 / 功效 / 见效 も)。体質などの結果には「傾向の目安で、医療的な診断ではありません」を必ず添える。
- アレルギーは「大丈夫」と言わず、スタッフに声をかけてもらう。
- この決まりは**テストで全部の文に当てる**(目で探すと漏れる)。新しい文は、グループの表現チェックの依頼書に番号を振って足す。

## 決裁者とのやり取りの型

- **結論から**。専門用語には一言の説明を添える(例: 「RPC(権限チェック付きの窓口)」)。
- 決めてもらうことは**選択肢+メリット・デメリット+おすすめ**で出し、「A / B」で返事できるようにする。1回に聞くのは4つまで。
- 本人の決定は日付つきで設計書・手順書に書く。**新しい決定が古い資料より優先**する。
- 確認をお願いするときは、**番号つきの手順と、開く URL と、見る所**を書く(「①日本語: 一番下までスクロールし、○○と出ているか」)。終わったら「全部できた」で返せるようにする。
- できなかったこと・確かめられなかったこと(例: 外部サイトが開けず URL を検索結果でしか確かめていない)は、隠さず最初に言い、本人に確かめてもらう方法を添える。
- 本人が使う道具に合わせる(例: 外部レビューに Codex のデスクトップアプリを使うなら、その AI が最初に読む `AGENTS.md` を同梱する)。

## 1機能を足すときの最小の型

1. **設計書**(`<機能>_DESIGN_<日付>.md`): 目的 → 決めること(1問ずつ、選択肢つき)→ 決定 → 画面 → データ → 権限 → 言葉づかい → 公開前に確かめること。
2. **DB**: `db/<番号>_<名前>.sql` と `_DOWN.sql`(戻し)を必ず対で。既存の関数は**署名と権限を変えずに置き換える**。バックアップと復元の対象に新しい表を足す。
3. **部品**(`app-core/*.mjs`): 判定・文言・画面用データ。DB と同じ判定を画面でも使うなら、**両者が一致することをテスト**する。
4. **画面**(`app-reference/*.html`): 文言は部品から。新しい要素には ID を付ける(テストが使う)。
5. **テスト**: DB(使い捨ての PostgreSQL)・部品・実ブラウザの通し(Playwright)。`run_tests.sh` の期待件数を更新し、**件数が減ったら失敗**にする。
6. **実装メモ**を設計書に追記: 作った物・関数名・要素 ID・設計書に書いていなかった細かい決め方・差し替える文の場所・まだのもの。
7. 本番に入れるのは承認のあと(`references/production-ops.md`)。

## 作業を始めるとき

1. 引き継ぎメモ・予行の実施記録・切り替え手順書の「現在地」を読む。決裁者の最新の決定を確かめる。
2. 変更する前に**テストを全部流して**、今の基準(件数)を確かめる。
3. 本番の状態は**読み取りだけ**で確かめる(DB の番号・運用の状態・設定値・会員数)。
4. 作業が終わったら、テスト全部 → コミット → 必要なら公開 → 記録の更新 → 決裁者に「何が変わったか・何を確かめてほしいか」を短く。
