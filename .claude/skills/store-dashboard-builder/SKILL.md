# 店舗向けダッシュボードの作り方

非エンジニアの意思決定者(例: 店舗の事業責任者)が、**スマホだけで見た目を確かめ、言葉で直しを頼み、最後は監査に出せる**状態まで持っていく。速さより「本番を壊さない」「決まったことを守る」「確かめたことだけを確かめたと言う」を優先する。

## 進め方の全体

1. 決まっていることを集める(依頼書・承認済みの見た目・最新の本人決定)
2. 守るべき約束を、テストとデータから機械的に抜き出す
3. 今のテストを先に流して、環境と基準を確かめる
4. 画面を作る(下の「設計の決まりごと」)
5. 自動テスト → 擬似データのプレビュー → 画面写真で確認
6. 公開版のプレビューを渡し、スマホで見てもらって直す(繰り返す)
7. 依頼書の変更追補・監査資料・引き継ぎメモを書く
8. 本番に触れる作業は、承認を得てから。実証は記録で示す

各段階の詳しい中身は下に書く。今日の失敗から学んだ注意点は `references/pitfalls.md`、資料の型は `references/doc-templates.md` にある。

## 1. 決まっていることを集める

- 引き継ぎメモ・依頼書(UI 契約)・承認済みのモック(見た目のイメージ)・本人の最新の決定を読む。**新しい決定が古い依頼書より優先**する。
- 依頼書の原本が手元にない(別の PC にある等)ときは、その事実を最初に伝え、モックと既存テストと引き継ぎメモから作る。監査資料にも「原本と突き合わせていない」と書く。
- 別の担当や別の PC に、未コミットの別版があることがある。どちらを残すかは本人に決めてもらう。勝手に混ぜない。

## 2. 守るべき約束を抜き出す

画面の約束は、依頼書よりも**テストのコードに正確に書いてある**ことが多い。推測せずに grep する。

- e2e テストが使う要素 ID・`data-tab`・`data-id`・**文言**(例: `#who:has-text('staff')`、`/確定しました: 100pt\(10円分\)/`)。文言を飾り直すとテストが落ちる。
- 権限の出し分けの確かめ方(例: 閲覧のみのアカウントでは `#adjust` が **DOM に 0 個**。隠すだけでは不合格)。
- データ API の返す項目名(DB の関数・クライアントのモジュールを読む)。画面に出す数字は、ここにあるものだけ。
- 旧版と新版の ID の差分は、最後に機械で取る(`references/pitfalls.md` のコマンド)。

## 3. 今のテストを先に流す

作業前に、変更なしの状態でテストを全部流す。通れば「この環境で検証できる」という事実になる(本人にとって価値がある情報)。落ちれば、自分の変更の前から落ちていると分かる。作業は使い捨てのコピー(git worktree など)で行うと安全。

## 4. 設計の決まりごと

**見た目**
- 白地+機能ごとの色(例: ポイント使用=ティール、会員=紫、集計=青)。成功=緑・注意=オレンジ・失敗=赤は、機能の色と別に固定する。
- ログイン直後は、いちばん使う業務(レジならポイント使用)を最上段に。ほかの機能は下のカードとタブから。
- 結果は「色・アイコン・文言」の3点セットで同じ場所に出す。確定は大きく、取消は離して小さく。
- ボタンは指で押せる大きさ(高さ 44px 以上、主要操作は 60〜76px)。数字は等幅数字(`tabular-nums`)。

**安全**
- 描画は `textContent` だけ。`innerHTML` を使わない(会員名にスクリプトが入っても実行されない)。
- 外部の CDN・Web フォントを読まない。アイコンはインライン SVG を `createElementNS` で組む。
- 権限の判定は DB 側。画面は補助なので、権限のない人には**部品を DOM ごと出さない**。
- 未取得の値は「—」。0 で埋めない。推測で値を作らない。

**数字と CSV(分析用)**
- 店長など限られた権限にだけ出す。氏名・LINE ID などの個人情報は入れない。
- 先頭が `= + - @` の文字列は `'` を付けて数式にさせない。Excel 用に先頭に BOM。
- 1件ずつ順番に取得する出力は、**厳密な同一時刻ではない**。「取得開始時刻」を列と画面に書く。API の上限(例: 履歴は直近100件)も列で明示する。
- 人数分の閲覧記録(監査ログ)が残る出力は、実行前に件数を見せて確認を取る。

**本人の決定で消す・変えるもの**は、消した理由と承認を後で依頼書の追補に書く(段階7)。店頭に不要な情報(元データの JSON、バックアップの時刻など)は画面から外し、必要なら別の仕組み(メールの見張り役など)に移す。

## 5. 検証

1. **自動テストを全部**流す(部分だけで合格と言わない)。
2. **擬似データのプレビュー**を作る:
   ```bash
   node scripts/make_preview.mjs --page <画面.html> --mock <擬似データ.js> --module <app-core/xxx.mjs> \
     --logo <ロゴ> --out <作業用フォルダ>/preview.html \
     --banner "プレビュー(擬似データ・本番に接続しません)。ログイン: mgr@t 店長 / staff@t / viewer@t、パスワード pw"
   ```
   擬似データは `assets/mock-supabase-example.js`(10ZEN のスタッフ画面の例: supabase-js の代わりに `auth` と `rpc` を返す)か、`assets/mock-kiosk-example.js`(店頭タブレットの QR 画面の例: ログインと、30秒ごとに変わる QR を返す関数の代わり)を写して、画面が呼ぶ関数に合わせて直す。QR コードのライブラリなど、ほかの `vendor/*.js` は自動で埋め込まれる。店長・スタッフ・閲覧のみの3アカウント、成功するコードと期限切れのコード、警告が出るデータ(不正の疑い・確定待ち)を入れておくと、全部の状態を見せられる。
3. **画面写真とはみ出しの確認**:
   ```bash
   node scripts/check_layout.mjs <作業用フォルダ>/preview.html <作業用フォルダ>/shots --login mgr@t pw --tabs redeem,members,dash
   ```
   はみ出したら、出てきた要素を見て直す(多いのは grid の列幅。`references/pitfalls.md`)。写真は自分の目でも見る(プレースホルダーの文字切れなどは数値に出ない)。
4. 権限ごと(店長・スタッフ・閲覧のみ)に、出てはいけない部品が DOM に無いことを確かめる。

## 6. スマホで見てもらう

- `make_preview.mjs` が出した `-pub.html` を、claude.ai のアーティファクトとして公開し、リンクを渡す(非公開。本人だけが見られる)。2回目以降は同じファイルを公開し直すと同じ URL のまま更新される。
- 渡すときに書くこと: ログインのアカウントとパスワード、試せる操作(成功するコード・期限切れのコード)、見てほしいところ、上部の帯と数字は擬似データであること。
- 直しの依頼は1つずつ確かめて直し、テスト → プレビュー更新 → 写真確認 → コミットまでを毎回やる。
- 「これは要りますか?」「アイデアをください」と聞かれたら、案を出して決めてもらう。依頼書から外れる変更(タブを消す等)は、その影響(依頼書の更新が要る)も伝える。

## 7. 資料を書く

`references/doc-templates.md` の型を使う。

- **依頼書の変更追補**: 変更一覧(原本→変更後→理由)、承認者と日付、要素 ID の維持・削除・追加、テストへの影響。原本は書き換えず、追補として一緒に保管してもらう。
- **監査資料**: 結論、本人の決定、本番に加えた変更と戻し方、変えていないもの、変更ファイル、設計、テスト結果、**確認できていないこと**、作業中に見つかったこと、監査で見てほしい点。本番の状態は**読み取りで確認した時刻つき**で書く(書き手の記憶で書かない)。
- **引き継ぎメモ**: 次のセッションが最初に読むもの。終わったこと・分かったこと・予定・判断待ち。
- 監査の指摘を受けたら、表で「指摘・対応・状況」を返し、本番の実証は記録(ログ・DB の行・届いたメール)で示す。

## 8. 本番の扱い

- 公開・DB の変更・本番の関数の更新は、本人の承認を得てから。承認は「何が変わり、何が変わらないか、どう戻すか」を添えて取る。
- 本番を更新する前に、本番で今動いている中身を読んで、リポジトリの基準と一致するか確かめる(違えば止まって報告)。
- 「メールが来なかった=正常」とは言わない。実行ログ・関数のログ・DB の記録で確かめる。
- 確かめていないことを確かめたと書かない。ネットワークの制限などで直接確認できないときは、そう書き、代わりの確認方法を示す。

## 進め方の注意(本人とのやり取り)

- 結論を先に、短く。専門用語には一言の補足をつける。
- 本人がスマホしか使えないときは、パソコンでの操作を求めず、プレビューのリンクで完結させる。パソコンでの操作が必要なときは、1画面ずつ手順を書き、スクリーンショットを送ってもらって進める。
- 許可の確認(承認画面)が一度に何十件も出る操作は避ける。まとめて画面で操作してもらうほうが早いことが多い。
- 公開リポジトリには、教材・内部資料・個人情報・秘密を入れない。

## お客様が見る画面(店頭タブレットなど)を作るとき

- 表示中の画面には、操作できる部品(ボタン・入力・リンク)を置かない。お客様が触っても管理の操作へ進めないようにする。テストで部品が 0 個であることを確かめる。
- 横置き・縦置き・スマホ幅の3つで写真を撮る。文字は遠くから読める大きさにし、手順は番号つきで3つ程度に絞る。
- 店頭の端末が眠らないよう、画面のスリープを防ぐ(使えない端末では何もしない)。
