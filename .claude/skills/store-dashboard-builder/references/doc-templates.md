# 資料の型

文体は「です・ます」なしの短い文。結論を先に。数字は表に。確かめていないことは、確かめていないと書く。

## 依頼書の変更追補(UI_CONTRACT_CHANGES_<日付>.md)

```markdown
# <画面名> 依頼書の変更追補(<日付>)

対象の依頼書: <ファイル名>(原本の場所)。この追補は原本に優先する。
- 決定者: <名前・立場>。<日付> に <どう確認したか> で承認。
- 実装: <ファイルのパス>(ブランチ <名前>)。

## 変更一覧
| # | 項目 | 原本 | 変更後 | 理由 |

## <特別な機能>の仕様
(CSV なら: 個人情報を含めない・数式対策・未取得は空欄・取得開始時刻・上限)

## 要素 ID と data-tab
| 区分 | 内容 |
| 維持 | ... |
| 削除 | ...(どの変更によるか) |
| 追加 | ... |
文言で守るもの(自動テストが確認している): ...

## テストへの影響
- 削除した ID をテストが参照していたか。直した実装。現在の合格件数。まだ確かめていないこと。

## 変えていないもの
```

## 監査資料(AUDIT_<日付>.md)

```markdown
# 監査用まとめ: <日付> の作業(<プロジェクト>)

対象リポジトリ・ブランチ・基準のコミット。

## 0. 本番の状態(読み取りで確認)
| 項目 | 値 |
| 確認時刻 | ... |
| 状態 | ...(いつ切り替わったか。自分の作業か) |
| 試験者の範囲 | ... |

## 1. 結論
## 2. 本人の決定(日付)        … 表
## 3. 本番に加えた変更          … 表(対象・変更・戻し方)。「変えていないもの」も書く
## 4. リポジトリの変更          … コミットとファイルの表
## 5. <画面>                    … 守っていること・依頼書との違い・動きの注意点
## 6. <周辺の仕組み>             … しくみ・安全面・残るリスク
## 7. テスト                    … 実行方法と、まとまりごとの件数の表
## 8. 確認できていないこと
## 9. 作業中に見つかったこと
## 10. 監査で見てほしい点
## 11. 未完了・判断待ち
## 12. 参照
## 13. 監査の指摘への対応(指摘を受けたら追記)
| # | 指摘 | 対応 | 状況 |
### 本番での実証の記録
| # | 確かめること | 実施 | 記録 | 結果 |
```

## 引き継ぎメモ(HANDOFF_<日付>.md)

```markdown
# 引き継ぎ: <日付>(<テーマ>)
作業ブランチ・基準。公開中のものを変えたかどうか。

## 終わったこと
## わかったこと
## 予定
## 判断待ち
## 次に話すこと / 最初の作業
```
