## 1. 目的

- **A. 来店の回数を増やす。**
- **C. 薬日本堂の相談・物販に案内する(送客)。**

## 2. ランクの基準(引き下げ)

累計ポイントで決まる。来店1回 100pt(1日1回)なので、来店回数の目安も書く。

| ランク | 今の基準 | 新しい基準 | 来店回数の目安 |
|---|---|---|---|
| WHITE OPAL | 0pt | 0pt(登録) | — |
| AMBER | 10,000pt | **1,000pt** | 10回 |
| EMERALD | 50,000pt | **3,000pt** | 30回 |
| RUBY | 100,000pt | **6,000pt** | 60回 |
| ONYX | 200,000pt | **10,000pt** | 100回 |

- **ランクは下がらない。** 累計ポイントは、ポイントを使っても減らない(今の仕組みのまま)。

## 3. 特典の中身

上のランクは、下のランクの特典も続けて使える。

| ランク | 到達のお祝い(1回) | その後ずっと使える特典 | 薬日本堂への案内(暫定) |
|---|---|---|---|
| WHITE OPAL | 登録で 100pt | 100pt=10円でお会計に使える | — |
| AMBER | 豆花 1つ | ディナーの五巡茶が無料(運営変更の前は1杯、後は飲み放題) | — |
| EMERALD | 持ち帰り用のお茶 1袋 | 季節ごとに豆花チケット1枚(年4枚) | 漢方相談の優待 |
| RUBY | 持ち帰り用のお茶 1袋 | 席・予約の優先案内 | 物販の優待 |
| ONYX | 持ち帰り用のお茶 1袋 | 新メニュー試食会へご招待 | 特別相談会など |

- **RUBY の「毎回5%OFF」は廃止する。** 費用が大きいため、費用のかからない優先案内に置き換える。
- **ランチの漢方茶は無料で飲み放題**(11〜15時)。このため「季節の薬膳茶1杯」はランチでは特典にならず、ディナーの漢方茶に置き換えた。
- **ディナーの漢方茶の飲み放題(300円)は、運営変更のタイミングで始まる予定。** それまでは「ディナーの漢方茶1杯が無料」。
- **持ち帰り用のお茶の原価は 10ZEN の負担。**
- **薬日本堂への案内は暫定案。** 薬日本堂側の了承が必要で、費用はかからない前提。運営変更の時期が決まったら相談する。

## 4. 使い方と数え方

| 種類 | 対象 | 使い方 | 数え方 |
|---|---|---|---|
| 1回で終わる特典 | 到達のお祝い・季節の豆花チケット | **コード方式。** 会員証のチケットで「使う」→6桁のコード→スタッフ画面で確定(ポイント使用と同じ流れ) | 使用済み・期限を DB で管理し、二重使用を防ぐ。確定した日時とスタッフを記録 |
| 来るたびに使える特典 | ディナーの漢方茶・優先案内 | 会員証のランクの色を見せる | **ダイニーに0円の商品**(例: 「会員特典 漢方茶(AMBER)0円」)を登録し、注文として入れる。ダイニーの CSV で数える |
| 招待 | ONYX の試食会 | こちらの仕組みから LINE で個別に招待 | 出欠をスタッフ画面で記録 |
| 薬日本堂への案内(暫定) | 相談・物販・特別相談会 | 会員証に「薬日本堂で見せる画面」を出す | 使った数は薬日本堂側で数える(形は相談のときに決める) |

- **画面写真の使い回しへの対策:** 会員証に「今の時刻」と、ゆっくり動く模様を出す。
- **集計で見る数字:** チケットの発行数・使用数・使用率、使った人が30日以内に再来店したか、薬日本堂への案内の数。

## 8. 実装メモ(2026-10-15)

- **状態:** 実装とローカルの自動テストまで。**本番の DB には適用していない**(公開・デプロイもしていない)。適用は 100・101 の後に `db/102_rank_perks.sql`。戻しは `db/102_rank_perks_DOWN.sql`(発行済みのチケットの記録も消えるので、先に `export_backup()` で保管する)。

### DB(`db/102_rank_perks.sql`)

- **ランクの基準:** `rank_thresholds` を 0 / 1,000 / 3,000 / 6,000 / 10,000 に変更。適用時に、会員のランクを累計で付け直す(基準を下げただけなので、上がるか変わらない。本番会員は既存の `_mirror` で customers のランク表示へ反映)。
- **新しい表**
  - `perk_ticket_types`: チケットの種類(到達のお祝い4種・季節の豆花1種)。品物の名前・有効日数・有効/無効は行の更新で変えられる。
  - `perk_tickets`: チケット1枚=1行(会員・種類・到達ランク または 季節・発行日時・期限・使用日時・確定したスタッフ・確定した申請)。お祝いは「会員×ランク」で1枚、季節の豆花は「会員×季節」で1枚(一意の索引)。
  - `perk_ticket_requests`: 「使う」の申請(6桁コード・期限・状態・確定日時・確定したスタッフ)。1枚のチケットで確定できるのは1回だけ(一意の索引)。
  - 3つとも anon・authenticated から直接は触れない(種類の表だけはスタッフが読める)。service_role も削除はできない。
- **お客様向けの関数(Edge Function の service_role からだけ)**
  - `app_me`(置き換え): 会員証を開いたときにチケットを発行し(`_issue_perk_tickets`)、`tickets`・`pendingTicket`・`lastTicket` を返す。定期実行は使わない。
  - `app_ticket_request(issuer, subject, ticketId, now)`: 本人の・未使用の・期限内のチケットに6桁コードを出す。有効時間はポイント使用と同じ `redeem_ttl_seconds`(180秒)。1人が同時に出せるチケットのコードは1つ(ポイントのコードとは同時に出せる)。
  - `app_ticket_cancel(issuer, subject, now)`: 表示中のコードを取り消す(チケットは残る)。
  - member-api の `action`: `ticket_request`(`ticketId` は UUID の形のみ。他は 400)・`ticket_cancel`。使えないときは 409(`ticket_not_found` / `ticket_used` / `ticket_expired` / `already_pending`)。
- **スタッフ向けの関数(ログイン済み。権限は関数の中で確認)**
  - `staff_lookup_code(code)`: スタッフ画面の入力欄はこれ1つ。チケットのコードならチケットの内容(`kind: "ticket"`)、そうでなければ従来の `staff_lookup_redeem` の結果(`kind: "points"`)を返す。空白入りの入力も通す。入力の間違いのロック(10分に10回)はポイントと共通。
  - `staff_confirm_ticket(requestId)` / `staff_cancel_ticket(requestId)`: 確定・取消。確定で `used_at`・`used_by` を記録し、監査ログに `ticket_confirm` を残す。コードを出した後に会員が停止・退会になっていたら確定せず、申請を取り消して `member_inactive` を返す(監査 L-1。`db/109_confirm_inactive_member.sql`。ポイント使用の確定 `staff_confirm_redeem` も同じ)。
  - `staff_ticket_stats()`: 発行数・使用数・使用率・未使用で期限切れ・今月の発行/使用・種類別・確定待ち。
  - 権限: コード確認・確定・取消は staff と manager だけ(viewer・kiosk・無効のアカウントは拒否)。集計は viewer 以上(kiosk は拒否)。凍結中は申請も確定も止まり、試験運用中は試験会員だけを扱う(ポイント使用と同じ)。
- **コードの重なりの防止:** ポイントのコードとチケットのコードが同時に同じ値にならないよう、両方の発行で同じロックを取って相手の表を確かめ、重なれば作り直す(`redeem_requests` にトリガー `redeem_code_not_in_tickets` を追加)。
- **バックアップ/復元:** `export_backup` / `restore_backup` に3つの表を追加。102 より前のバックアップ(表がない)は、そのままでは基準の一意の決まりにぶつかって復元できなかった(監査 AUDIT_20261015.md の M-1)。**`db/108_restore_old_backup_fix.sql` で修正:** 102 より前のバックアップでは基準は今の DB の値(新しい基準)を残し、会員のランクを累計から今の基準で付け直す(102 の適用時と同じ)。102 以降のバックアップでは、基準を重ならない値へ一度ずらしてからまとめて置き換える。本物の古いバックアップでの検証は `patches/test_restore_old_backup.mjs`。

### 決め方(設計書に書いていなかった細かい点)

- **到達のお祝いの期限「発行から60日」:** 発行した日(日本時間)から数えて60日目の終わりまで(例: 10/15 発行 → 12/14 まで)。
- **飛び越しのルール(7章の案):** 一度に複数のランクを上がったら、到達した一番上のランクのお祝いだけを出す。その後さらに上がれば、そのランクの分を出す。102 の適用時点で累計が多い会員も、次に会員証を開いたときに今のランクの分だけが出る。
- **季節の豆花:** EMERALD 以上の会員が、その季節に会員証を開いたときに1枚出る(季節の途中で EMERALD に上がった場合も、その季節の分から)。**その季節に一度も会員証を開かなかった会員には、その季節の分は出ない**(定期実行を使わない設計のため)。季節は日本時間で区切る(冬は 12〜2月。冬の鍵は12月の年。例 2026-winter は 2026/12〜2027/2)。期限は季節の最終日の終わり。
- **会員証の「その後ずっと使える特典」(文字だけ):** AMBER「ディナーの五巡茶 無料」、EMERALD「季節の豆花チケット(季節ごとに1枚)」、RUBY「席・予約の優先案内」、ONYX「新メニュー試食会へご招待」。上のランクは下の分も出す。EMERALD 以上に「薬日本堂のご優待(準備中)」を小さく添える。RUBY の 5%OFF は会員証・店頭QR画面のどちらにも書かない。
- **ディナーの漢方茶の文言:** 運営変更の前後(1杯/飲み放題)は書き分けず「無料」とだけ出す。

### 画面

- **会員証(card.html):** 新しい要素 ID は `liveClock`(表面の時刻。日本時間 HH:MM:SS・毎秒更新)、`tickets`(チケットの一覧。各「使う」ボタンに `data-ticket-id`)、`ticketPending` `ticketPendingInfo` `ticketCode` `ticketLeft` `ticketCancel`(コードの表示)、`lastTicket`(直近の結果)、`rankPerks`(いまのランクの特典)。表面にゆっくり動く斜めの模様を重ねる(動きを減らす設定では模様と点滅を止め、時刻は更新し続ける)。コードの表示中は3秒ごとに確認し、スタッフが確定すると「○○ をご利用いただきました」と出る。
- **スタッフ画面(staff.html):** 入力欄 `#code` と `#lookup` はそのまま。チケットのときは `#rAmount` の代わりに `#rTicket`(特典名と期限)を出し、確定・取消はチケットの関数を呼ぶ。集計に `#ticketStats`(発行・使用・使用率)を追加。確定待ちのチケットがあれば警告を出す。B案の色・textContent だけ・CDN なし・インラインの SVG のまま。依頼書の追補(UI_CONTRACT_CHANGES_20261014.md)で守る ID・文言は変えていない。
- **店頭のQR画面(qr.html):** KIOSK_COPY の特典とランクの文言を新しい特典に変更(5%OFF・薬膳茶・スイーツの記述を削除)。操作できる部品は0個のまま。`tools/test_kiosk_copy.mjs` が、10円・豆花・漢方茶・お茶・優先案内・試食会の要点と「○○pt達成」の数字を、会員証と DB の基準に照らして確認する。
