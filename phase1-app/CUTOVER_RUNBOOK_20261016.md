## 4. 旧会員の引き継ぎ(D-1 で「引き継ぐ」と決めた場合だけ)

1. 引き継ぎの前に、**新しいランクの基準で何人がどのランクになり、お祝いのチケットが何枚発行されるか**を数えて、牧野さんに見せる(基準を下げたため、上のランクの人が多く出る可能性がある)。
2. 方針を決め直す: `decide_policy('migration_scope', …)`、累計の扱い `decide_policy('lifetime', 'confirmed_per_member' または 'use_floor_estimate')`。
3. 旧システムの会員の一覧(手順2の `snapshotUsers()` の結果。会員番号・LINE の ID・ポイント・累計・最終来店日)から、1人ずつ `import_opening_balance` で取り込む(凍結中だけ動く。同じ人を2回取り込んでも二重にならない)。**取り込み用の道具はまだ無いので、引き継ぐと決めたら先に作ってテストする。**
4. 累計を確定する場合は `confirm_lifetime_base`(1人1回、取り込んだ残高以上)。
5. `cutover_report()` で、1人ずつの取り込み時の残高と今の残高を控える(戻すときの基準)。

- ダイニー導入後: 注文ボタン用に、ダイニーの店舗IDと LIFF ID を設定する(どちらも導入時に発行される)。注文 URL の形は `https://web.self.dinii.jp/gateway?liffId=…&shopId=…&tableCode=…`(2026-10-21 回答)。**ダイニーのテスト用のテーブルで、お席の QR → 体質チェック → 注文 → 会計までを実機で通してから**お席に置く。特典の0円商品は、ダイニーの管理画面「取扱メニュー」で登録し、公開設定を「お客様」OFF・「スタッフ」ON にする(新規作成時はすべて ON なので手で OFF。2026-10-21 回答)。案: 「会員特典 五巡茶飲み放題」「ご登録の特典 五巡茶飲み放題」「お友だち紹介 五巡茶飲み放題」。名前はお客様の注文履歴に出る。レシートには0円で載せる(2026-10-21 牧野さん決定。「レジ設定」の0円の表示は ON のまま=初期設定)。出数は「POSデータ分析 > 商品分析」で数える。
- テーブルを追加・削除すると、そのテーブルの注文 URL が変わる。ダイニーから URL の一覧(CSV)を受け取り、お席の QR カードを作り直す(名前・エリア・並び替えだけなら変わらない)。
- ダイニー導入後: **お席に置く QR**(体質チェック → そのまま注文)を `app-reference/table-qr.html` で作って印刷する。入れるのは「表示名,テーブルコード」(テーブルコードはダイニーの席の QR の `tableCode`)。本番の LIFF(N7nKgExB)で組み立てた画面で作ること(試験の LIFF で作った QR は本番では使わない)。ダイニーの店舗IDと LIFF ID を設定した画面で作ると、同じカードに「すぐにご注文の方はこちら」(そのテーブルの注文 URL。LINE を使わない方も注文できる)の QR も並ぶ。
- バックアップの保存先を 10ZEN の Google アカウントに移す(見張り役は別のアカウントのまま)。

## 9. 予行演習(2026-10-15〜16)で分かったこと

- Supabase の API 経由では、WHERE のない UPDATE が安全装置に止められる(DB 111 で修正済み。テストで見張っている)。
- 外部ライブラリの「最新版」を取りに行く書き方は壊れることがある(関数の取り込みは版を固定済み)。
- 大きな SQL を送ると通信が途中で切れる。DB に固定したコミットのファイルを取得させ、中身(md5)と結果(指紋)が手元と一致したときだけ適用する方式が確実。
- 来店の受付時間の外(10:55)では、正しく断られた。
- 試験用の会員の画面・スタッフ画面・特典チケット・体質チェックは、iPhone で通しで動いた(友だち紹介は確認中)。
