## 2. 指摘一覧

### 中

#### M-1. 102 より前に取ったバックアップが、102 以降の DB に復元できない

- **何が問題か:** ランクの基準の表(`rank_thresholds`)の「必要なポイント」の列は、重複を許さない決まり(一意)になっている。102 は基準を 0/1,000/3,000/6,000/10,000 に下げた。102 より前のバックアップには古い基準(0/10,000/50,000/100,000/200,000)が入っている。復元の関数はこれを1行ずつ上書きするので、AMBER を 10,000 に戻した瞬間に、すでに 10,000 の ONYX とぶつかって**復元全体がエラーで止まる**。
- **起こりうる被害:** 102〜107 を本番に入れた後に障害が起き、**入れる前の日のバックアップから戻したい**とき(例: 移行の失敗で前日の状態に戻す、新しいプロジェクトに作り直す)に、復元ができない。手作業で JSON を書き換えるまで復旧が止まる。また、仮に順番の都合で通った場合でも、**古い基準が新しい基準を黙って上書き**し、ランクの判定が旧ルールに戻る。
- **再現の手順(実施済み):** 使い捨ての DB に 100・101 だけを入れて会員を1人登録 → `export_backup()` を取る(基準は 0/10000/50000/100000/200000)→ 別の空の DB に 100〜107 を入れて、そのバックアップを `restore_backup()` → `ERROR: duplicate key value violates unique constraint "rank_thresholds_min_points_key"` で失敗。
- **根拠:** `db/100_phase1_schema.sql:47`(`min_points ... unique`)、復元の上書き `db/102_rank_perks.sql:356-357`(103 の `:312-313`、105 の `:311-312`、106 の `:447-448` でも同じ文)。テストは**新しい DB から取ったバックアップから表を消して**「古いバックアップ」の代わりにしているため、基準が新しいままで、この問題を見逃している(`patches/test_rank_perks.mjs:258`、同様に test_constitution・test_kpi・test_referral)。
- **直し方の提案:**
  1. 復元の方針を決める: 「基準は**今の DB の値を残す**(バックアップの基準は使わない)」が安全(ランクの基準は会員のデータではなく設定のため)。その場合は `rank_thresholds` の上書きをやめ、`label` だけ合わせる。バックアップの基準を使いたい場合は、上書きの前に全行の `min_points` を一時的に重ならない値へずらしてから入れ直す。
  2. 復元のあと、会員のランクを今の基準で付け直す(102 の適用時と同じ処理)。
  3. テストに「100・101 だけの DB で取った本物の古いバックアップ」を復元する検証を足す。
  4. 直すまでの運用: 102 以降を入れた後に古いバックアップから戻す必要が出たら、「100・101 だけの空の DB に復元 → 102〜107 を順に適用」の順で行う。手順書に1行書いておく。この順で通ることはローカルで確認した(復元は成功し、102 の適用で基準が新しくなり、累計 3,000pt の会員は EMERALD に付け直され、残高の不一致は0件)。

### 低

#### L-1. 停止中の会員のチケットも、スタッフが確定できる

- **何が問題か:** チケットのコードの確認(`staff_lookup_code`)と確定(`staff_confirm_ticket`)は、会員が「停止中」かどうかを見ていない。お客様がコードを出した後に店長が会員を停止しても、そのコードはスタッフ画面で確定できる。
- **起こりうる被害:** 不正で停止した会員に、停止の直後(コードの有効時間 180 秒の間)に特典を渡してしまう。影響は小さい(ポイント使用の確定 `staff_confirm_redeem` も従来から同じ動き)。
- **根拠・再現:** `db/102_rank_perks.sql:239-249`・`:256-285`。ローカルで「コード発行 → 会員を停止 → スタッフが確認 → 確定」を試し、`confirmed` になった。
- **直し方の提案:** 確定の前に `m.status = 'active'` を確かめ、違えば申請を取り消して `member_inactive` を返す(ポイント使用の確定にも同じものを足す)。

#### L-2. 五巡茶の出し方の切り替えが、試験運用中でも本番の会員のチケット名を書き換える(凍結中も動く)

- **何が問題か:** `manager_set_dinner_tea_mode` は、状態(`test`・`frozen`)や会員の区分(試験/本番)を見ずに、**すべての**まだ使っていない紹介のチケットの名前を書き換える。ほかの書き込みの関数は「試験運用中は試験会員だけ」「凍結中は止める」を守っている。
- **起こりうる被害:** 予行(`test`)の中で店長が「飲み放題」に切り替えて試すと、本番の会員のチケットの名前も変わる(いまは本番の会員が 0 人なので実害はない)。名前が変わるだけで、使える回数や期限は変わらない。
- **根拠・再現:** `db/106_referral.sql:307-321`。ローカルで `test` の状態で切り替え → 本番の会員の紹介のチケットの名前が「飲み放題」に変わった。`frozen` でも切り替えられた。
- **直し方の提案:** 設定は全体で1つのままでよいが、名前の書き換えは「いまの状態の区分の会員のチケットだけ」にする。または、名前をチケットに保存せず表示のときに設定から作る。凍結中は止めるかどうかを決めて、設計書に書く。

#### L-3. 体質チェックの個人の結果を、スタッフ(店長以外)が一覧でまとめて見られる。誰の結果を見たかが一覧では記録されない

- **何が問題か:** 会員の一覧(`staff_list_members`)は、スタッフにも全会員の「あなたの体質」のタイプを返す(1回 100 人まで)。会員の詳細を開いたときは閲覧の記録(`view_member`)が残るが、一覧は「一覧を開いた」ことしか記録されない。閲覧(本部)には返さない作りは正しく動いている。
- **起こりうる被害:** 個人の体質の情報が、同意の文(「結果を会員証に記録し、おすすめとお店づくりに役立てます」・まだ確認前)で想定した範囲より広く見られる可能性。体質の情報は診断ではないが、健康に近い情報としてお客様が気にする種類のもの。
- **根拠:** `db/107_constitution_each_visit.sql:190-210`(一覧)・`:228`(閲覧には返さない)。設計書 `CONSTITUTION_CHECK_DESIGN_20261015.md` の 11章「まだのもの」にも同じ懸念が書かれている。
- **直し方の提案:** 同意の文の確認のときに「店舗のスタッフがおすすめのために見る」ことを明記する。一覧のタイプの印が本当に必要かを牧野さんに確認する(詳細だけで足りるなら一覧からは外す)。外さない場合は、一覧の記録に「体質の印を返した」ことを残す。

#### L-4. 新しい member-api を DB の 106 より先に公開すると、招待のリンクからの登録が失敗する

- **何が問題か:** 新しい member-api は、招待コードがあるときだけ DB に新しい引数を渡す。DB が 106 より前だと、その登録は 500 エラーになり、**友だちは会員登録そのものができない**。チケット・体質チェックの新しい操作も、DB が 102・103 より前なら 500 になる。
- **起こりうる被害:** 公開の順番を間違えたときに、紹介で来た友だちが登録できない。
- **根拠:** `functions/member-api/handler.ts:92-93`。手順は `REFERRAL_AND_REPORT_DESIGN_20261015.md` の A-5 の1番目に「member-api より先に DB」と書かれており、実害は手順を守れば起きない。
- **直し方の提案:** 本番反映の手順(4章)の順番を必ず守る。念のため、member-api で `app_register` が「関数が見つからない」で失敗したときは、招待コードなしで登録し直す(紹介にはならないが登録はできる)作りにしてもよい。

#### L-5. レジの客数の取り込みで、画面と DB の上限が違う。分けて送るので途中まで入ることがある

- **何が問題か:** 画面の読み取り(`parseCount`)は客数を 7 桁(〜9,999,999)まで受け付けるが、DB は 1 日 100,000 人までしか受け付けない。1 行でも上限を超えると、その回(400 行)はまとめて拒否される。400 行を超えるファイルは複数回に分けて送るので、途中の回で失敗すると前の回の分だけが入る。
- **起こりうる被害:** 誤ったファイルを選んだとき、エラーの理由が分かりにくい。途中まで入った状態になる(画面は「もう一度押すと続きを取り込みます」と案内しており、同じ日は上書きなので、やり直せば整う)。データの改ざんや情報の漏れにはつながらない。ファイルの大きさの上限もないが、店長が自分の端末で読むだけなので影響は本人の端末に限られる。
- **根拠:** `app-core/pos-import.mjs:67-71`、`db/105_kpi.sql:231`、`app-core/staff-client.mjs:55-62`。
- **直し方の提案:** 画面でも 100,000 を超える日を「確かめてほしい日」として印を付けて除く。ファイルの大きさに上限(例: 5MB)を付ける。

#### L-6. テスト用の使い捨て DB が後片付けされず、作業環境のディスクを埋める

- **何が問題か:** テストのたびに `/tmp/pgt-*` に使い捨ての PostgreSQL のデータ(1つ約 45〜70MB)を作るが、終わっても消さない。また、ポート番号が固定(55433)なので、テストを2つ同時に動かすとぶつかる。
- **起こりうる被害:** 今回の監査の開始時点で、**ディスクが 100% 埋まっていた**(残り 23MB。古い `/tmp/pgt-*` が約 650 個・約 30GB)。この状態では一括テストが `initdb` で失敗し、「合格 112 件・失敗したスイート 16 件」という、コードの問題と見分けにくい結果になった。古いディレクトリを消して(動いている PostgreSQL がないことを確かめてから)再実行し、257 件合格を確認した。
- **根拠:** `patches/pgdb.mjs:16`(作成)・`:20`(固定のポート)・`:37`(停止だけで削除しない)。
- **直し方の提案:** `stop()` で `rm -rf` までする(`fs.rmSync(base, { recursive: true, force: true })`)。`run_tests.sh` の最後でも `/tmp/pgt-*` を消す。ポートは空いているものを選ぶ。

## 3. 確認できたこと(安全と判断したもの)

ローカルの使い捨て DB(100〜107 を適用)で、実際に呼び出して確かめた。

**権限**
- 新しい SECURITY DEFINER の関数は**すべて `search_path` が固定**されている(固定されていない関数は0個)。
- `anon`(未ログイン)が実行できる関数は**0個**。新しい表はすべて行レベルセキュリティが有効で、`anon`・`authenticated` からは直接読めない(読めるのは従来の設定3表と、スタッフ向けのチケットの種類の表だけ)。`service_role` も新しい表を削除できない。
- 内部の関数(`_kpi_overview`・`_issue_perk_tickets`・`_cc_profile`・`_referral_reward` など)と `report_monthly` は、店長のアカウントからでも「権限なし」で拒否された。お客様向けの関数(`app_*`)はログインしたスタッフからは呼べない(`service_role` だけ)。
- 役割ごとの結果(試した結果):

| 関数 | 店頭タブレット | 閲覧(本部) | スタッフ | スタッフ以外 |
|---|---|---|---|---|
| コードの確認・チケットの確定・取消 | 拒否 | 拒否 | 可 | 拒否 |
| チケットの集計・紹介の集計 | 拒否 | 可 | 可 | 拒否 |
| 体質チェックの集計 | 拒否 | 全部 | 今週の傾向だけ | 拒否 |
| 目標と KPI | 拒否 | 可(見るだけ) | 拒否 | 拒否 |
| 店長の変更(五巡茶・本番開始日・目標・レジの客数) | 拒否 | 拒否 | 拒否 | 拒否 |

- 閲覧(本部)には、会員の詳細・一覧とも、個人の体質の情報をキーごと返さない(コードと既存のテストで確認)。

**不正・二重**
- お客様 B が、お客様 A のチケットの ID で「使う」を送ると `ticket_not_found`(他人のチケットは操作できない)。
- 同じチケットの確定を2つ同時に送ると、1つは `confirmed`、もう1つは `already_confirmed`。使用済みは1枚だけ。使用済みのチケットにもう一度コードは出ない。
- ポイントのコードとチケットのコードは、同じ値が同時に有効にならない(チケットのコード `111111` が有効な間に、ポイントのコード `111111` を作ろうとすると拒否される)。入力の間違いのロック(10分に10回)はポイントとチケットで共通。スタッフの入力欄は空白入りでも通る。
- 紹介: 招待コードは推測できない12文字(72ビットの強い乱数)で、会員番号を含まない。紹介者1人あたり暦月5人で、6人目は `over_cap`。月の境目は日本時間(10/31 23:59 は10月の6人目で上限、11/1 0:00 は11月の1人目で受付)。初来店の特典は1回だけ(同じ日の2回目・翌日の来店では出ない)。自分自身のコードは使えない(登録の時点で自分はまだ会員でないため)。旧ルール(会員番号での紹介・登録時の +100pt)は無効。
- 体質チェックの点数・タイプは、画面から送られた値を使わず、回答から DB が計算する(member-api も点数を受け取らない)。
- レジの客数の取り込みは、日付・客数の形・未来の日付・重複・400行の上限を DB が確かめ、上書きした日は前後の値を監査ログに残す。売上は送らない・保存しない。

**トークン(backup-export)**
- 月次レポート用のトークンで呼べるのは `monthly_report` だけ(`status`・`export`・`record` は 403)。見張り用のトークンでは `monthly_report` は 403。全体のトークンの範囲は変わっていない。比較は長さが同じときに全文字を比べる方式(時間差で推測されにくい)。`handler.ts:30-42`。
- 月次レポートの中身は集計の数字だけ。氏名・会員番号・LINE の ID・会員の内部 ID・招待コードは含まない(既存のテストで確認)。レジの取り込みのファイル名も含まない。

**画面**
- 新しい画面・部品は、表示を `textContent` と `createElement`/`createElementNS` だけで作っている。`innerHTML`・`insertAdjacentHTML`・`document.write`・`eval` は使っていない。外部の CDN は読み込んでいない(同じ場所の `config.js`・`vendor/*.js` だけ)。
- `localStorage`(今日はスキップ)と `sessionStorage`(招待コード)の読み書きは、すべて try/catch で囲まれ、使えない端末でも動く。
- `?ref=` のコードは「12文字の英数字と - _」の形だけを受け付け、URL からはすぐ消す。外へのリンク(LINE の送る画面・薬日本堂・地図・予約)は固定の URL で、別のタブで開くものには `noopener noreferrer` が付いている。招待のリンクは `encodeURIComponent` で組み立てている。
- CSV の新しい列(体質タイプ・実施日)も、既存の「先頭が = + - @ の文字列は数式にしない」加工を通る。

**データの整合**
- 戻し(DOWN)は、置き換えた関数の中身と権限を1つ前の状態に正確に戻す(既存のテストが関数の定義の一致で確認)。新しい番号から順に戻す必要がある(例: 103 の前に 104)。
- バックアップ/復元は新しい表をすべて含み、**102 以降の DB から取ったバックアップ**は復元できる(古いバックアップは M-1 を参照)。
- 試験/本番の区分(`is_test`)は、新しい集計・書き込みの関数で一貫している(例外は L-2 の名前の書き換えだけ)。日本時間の日付の境目は、チケットの期限・季節・紹介の月・来店時の実施率でテスト済み。
- 性能: 擬似データ(会員5,000人・来店4万件・体質チェック7,500件)で、会員の一覧 約45ミリ秒、目標と KPI(13か月)約0.45秒、体質チェックの集計 約55ミリ秒、月次レポート 約0.17秒。Free プランで問題ない速さ。
