## 1. 位置付けと方針

- **ターゲット:** 販促計画(2026-08)のとおり、ライトな健康志向の方(20〜30代の女性や会社員など)。「美味しいから来て、気づけば健康に」。専門的な健康志向の方には寄せない。
- **10ZEN の位置付け:** 薬日本堂との相互送客の入り口。
- **言葉:** 難しいことを並べない。正しい理論と正式な名称を裏に持ち、表はわかりやすくする(3段構え)。
  1. **表に出す言葉:** 例「モヤモヤ渋滞タイプ」とひとことの説明。
  2. **正式な名称:** タップした人だけに見せる。五行・五臓・状態の名称。
  3. **次の一歩:** 「もっと詳しく知りたい方は、薬日本堂の漢方相談へ」。
- **名前:** 「1分体質チェック」(旧「30秒体質チェック」。15問になったため変更)。

## 2. タイプ(五行の5タイプ)

| 五行 | 五臓 | 状態の名称 | 表に出す言葉 |
|---|---|---|---|
| 木 | 肝 | 気滞(きたい) | モヤモヤ渋滞タイプ |
| 火 | 心 | 偏熱(へんねつ) | カッカ熱こもりタイプ |
| 土 | 脾 | 脾虚(ひきょ) | 消化パワー不足タイプ |
| 金 | 肺 | 燥(そう)・津虚(しんきょ) | うるおい不足タイプ |
| 水 | 腎 | 陽虚(ようきょ) | ぽかぽかパワー不足タイプ |

- 旧版(Marquiz・本番 DB の `diagnosis_patterns`)からの変更: 火を「湿熱」から「偏熱」へ、金を「陰虚」から「燥・津虚」へ。教材の五行配当表で、湿は土・燥は金の気候にあたるため。
- **正式な名称は、公開前に薬日本堂の方に確認してもらう。**

## 3. 質問と判定

**答え方:** 全問「よくある(2点)/ときどき(1点)/あまりない(0点)」の3択。

| 五行 | 質問 |
|---|---|
| 木 | 1. イライラしたり、気分の浮き沈みが大きい / 2. 目が疲れやすい・かすみやすい / 3. ため息が多い・お腹や胸が張る |
| 火 | 4. 寝つきが悪い・夢をよく見る / 5. 顔がほてる・赤くなりやすい / 6. ドキドキしやすい・汗をかきやすい |
| 土 | 7. 食後に眠くなる・胃がもたれる / 8. むくみやすい・湿気の多い日はだるい / 9. 考えすぎると食欲が落ちる・甘いものが欲しくなる |
| 金 | 10. 肌・髪・のどが乾燥しやすい / 11. 風邪をひきやすい・鼻やのどの不調が出やすい / 12. 便が硬い・出にくい |
| 水 | 13. 手足や腰が冷えやすい / 14. 夜中にトイレに起きる・トイレが近い / 15. 腰や膝がだるい・髪のハリが気になる |

- **16. 食事の気分(5択):** 選択肢はメニューが決まったら差し替える(メニューの設計は別件)。
- **判定:** 五行ごとの合計(0〜6点)を比べ、一番高い五行が主なタイプ。**同点は今の季節の五行を優先**(春=木・夏=火・土用=土・秋=金・冬=水)。**全部1点以下は「バランス良好」**。
- 旧版の判定(桁の優先順で、木が1つでもあれば木)は木に偏るため廃止。

## 6. 五巡茶(薬日本堂)の日替わり

- **漢方茶を薬日本堂の「五巡茶」(木・火・土・金・水の5種)に変える予定。** 表記は「五巡茶」で統一する。
- **曜日の名前どおりに出す:** 火曜=火、水曜=水、木曜=木、金曜=金、土曜=土。月曜・日曜=今の季節の五行。
- 1日1種類を、温かいもの・冷たいものの両方で出す。ランチは無料で飲み放題、ディナーは有料の飲み放題(AMBER 以上は無料。ランク特典の設計を参照)。
- 体質のタイプと同じ五行のお茶を「あなたのお茶」とする。
- **水の五巡茶:** 原材料にはとむぎ(教材では微寒)などを含むため、冷えのタイプの方には「温かいほうで」と添える。

## 10. 実装メモ(2026-10-15)

- **状態:** 実装とローカルの自動テストまで。**本番の DB には適用していない**(公開・デプロイもしていない)。適用は 100・101・102 の後に `db/103_constitution_check.sql`。戻しは `db/103_constitution_check_DOWN.sql`(結果・同意・今日の体調・クリックの記録も消えるので、先に `export_backup()` で保管する)。

### DB(`db/103_constitution_check.sql`)

- **新しい表**(4つとも行レベルセキュリティあり。anon・authenticated から直接は触れない。service_role は読み取りと追記だけ)
  - `constitution_consents`: 同意(会員×版。版は `constitution_v1`・同意した日時)。
  - `constitution_checks`: 1回=1行。15問の回答(`answers`)・食事の気分(`mood`)・五行ごとの点数(`score_wood` 〜 `score_water`)・主な五行(`primary_element`)・バランス良好(`balanced`)・実施した季節(`season_key`。例 2026-autumn)・その日の季節の五行(`season_element`)・日時。
  - `constitution_daily_conditions`: 今日の体調(会員×日本時間の日付で1行)。A=`temp`(cold/hot/normal)・B=`energy`(tired/stress/fine)・C=`concern`(dry/swelling/none)・今日のおすすめの五行(`focus_element`)・もとにした結果(`check_id`)。
  - `constitution_referral_clicks`: 「薬日本堂の漢方相談へ」が押された記録(会員・最新の結果・日時)。
  - `app_settings` に `constitution_moods`(食事の気分のコード。仮)を追加。
- **判定の関数**(誰からも直接は呼べない): `_season_element`(季節の五行)・`_cc_pick`(一番高い五行と同点の決め方)・`_cc_result`(15問→点数・タイプ・バランス良好)・`_cc_focus`(今日の体調の足し算)・`_tea_of_day`(五巡茶の日替わり)・`_constitution_snapshot`(会員証に出す情報)。
- **お客様向けの関数(Edge Function の service_role からだけ)**
  - `app_constitution_submit(issuer, subject, answers int[15], mood, consent, now)`: 点数・タイプは受け取らず、回答から計算する。同意の行がなく `consent` が true でなければ `consent_required`(記録しない)。不正な回答は `invalid_answers`、設定にない気分は `invalid_mood`。1時間に20回まで。
  - `app_condition_submit(issuer, subject, temp, energy, concern, now)`: 日本時間の1日に1回(2回目は `already_answered`)。結果がまだなければ `no_check`。
  - `app_referral_click(issuer, subject, now)`: 押された数を記録(1時間に30回を超えた分は数えない)。
  - `app_me` は `_member_view` の置き換えで、`constitution`(最新の結果の要約と `seasonChanged`)・`constitutionConsent`・`todayCondition`・`todayTea`・`yourTea`・`season` を返す(チケットの関数の応答にも入る)。
  - member-api の `action`: `constitution_submit`(`answers` は 0〜2 の整数15個・`mood` はコードの形・`consent` は真偽値のみ。それ以外は 400。`scores` などを送っても使わない)・`condition_submit`・`referral_click`。同意がないときと、回答済み・未実施のときは 409。
- **スタッフ向けの関数:** `staff_constitution_stats()`。店長・閲覧(本部)は `scope: "full"` で、実施人数・実施率・タイプ別・五行ごとの平均・再来店率と来店頻度の比較・相談ボタンの数(累計・今月)・今週の体調。スタッフは `scope: "limited"` で今週の体調(`week`)だけ(ほかの項目は応答に含めない)。店頭タブレット・スタッフ以外は拒否。いまの状態の会員だけ(試験運用中は試験会員だけ)を数え、個人の結果は返さない。
- **バックアップ/復元:** `export_backup` / `restore_backup` に4つの表を追加。103 より前のバックアップも復元できる。

### 決め方(設計書に書いていなかった細かい点)

- **土用の日付:** 立春・立夏・立秋・立冬の前の約18日を、年によらない固定の日付で近似した(1/17〜2/3・4/17〜5/4・7/20〜8/6・10/20〜11/6、両端を含む。日本時間)。実際の土用の入りは年により1日ほど前後する。
- **同点:** 季節の五行が同点に入っていればそれ、入っていなければ 木・火・土・金・水 の順で先のもの。今日の体調の足し算も同じ。
- **バランス良好の「あなたのお茶」:** 同じ決め方で選んだ五行のお茶(全部同点なら季節の五行)。正式名称は出さない。
- **季節が変わったときの案内:** 春夏秋冬(12〜2月=冬。102 の季節と同じ)で比べる。土用では案内しない(18日ほどで二度出さないため)。
- **今週の体調の傾向:** 直近7日(日本時間・今日を含む)。
- **再来店率・来店頻度:** 直近60日(日本時間・今日を含む)に来店記録が2日以上ある会員の割合と、来店記録の日数の平均。登録日の来店扱い(`register_counts_as_visit`)も1日と数える。実施した/していないは「一度でも実施したか」。タイプ別・平均は会員ごとの最新の結果。
- **今日の体調を出す場面:** 会員証で、その日に来店記録があり(`visitedToday`)、体質チェック済みで、今日まだ答えていないとき。DB は来店を必須にしていない(任意の回答のため)。
- **今日のおすすめの一品:** 今日の体調に答えていればその五行、なければ体質の五行 × 食事の気分。
- **水の五巡茶の「温かいほうで」:** 承認済みのお茶のひとことに含まれるので、別の注記は重ねて出さない。
- **同意の文:** 設計書の「お店の改善に使います」は、言葉づかいのきまり(「改善」を使わない)に合わせて「結果を会員証に記録し、おすすめとお店づくりに役立てます。」に言い換えた(確認前)。

### 決め方(決定に書いていなかった細かい点)

- **平均の取り方:** 会員の結果を新しい順(日時、同じ日時は記録の順)に並べた最新の3回。**同じ日に何回チェックしても、それぞれ1回と数える**(決定の「最新の3回」のとおり。1日1回に絞らない)。
- **平均の同点:** 「平均に入れた回のうち**最新の回**の季節の五行」を優先し、それでも決まらなければ 木・火・土・金・水 の順。見る日の季節ではなく最新の回の季節にしたのは、1回だけのときに「あなたの体質」がその回のタイプと必ず一致し、日によって変わらないようにするため。比べるのは五行ごとの合計(回数が同じなので平均と同じ順で、割り算の端数の誤差が出ない)。
- **平均のバランス良好:** 平均がすべて1点以下(**ちょうど1点を含む**。例: 2点の回と0点の回の平均は1点 → バランス良好)。1回ずつはバランス良好でなくても、平均でバランス良好になることがある。
- **平均の見せ方:** DB は小数2桁(四捨五入)で返す。画面の五角形の数字は小数1桁。
- **「今日」:** 日本時間の日付。「今日チェックしたか」は、日本時間のその日にその会員の結果が1つでもあるか。
- **スキップの記録:** 端末の `localStorage`(キー `10zen_cc_skip`、値は日本時間の日付)。読み書きは try/catch で囲み、使えない端末ではその画面を開いている間だけ隠す(再読み込みでまた出る)。サーバーには送らない(数えない)。

## 追補(2026-10-16): お席の QR からの注文・Web 版の体質チェック(牧野さん承認)

**お席の QR → 体質チェック → そのまま注文**
- 来店ポイントを付けるのは帰りが多い(牧野さん)ため、「来店した日だけ注文ボタン」では足りない。お席に QR(`check.html?table=<テーブルコード>`)を置き、そこから入った人には、結果の「このまま注文する」で読み直さずにそのテーブルのダイニーの注文画面を開く(`app-core/dinii.mjs` の `diniiTableUrl`。LIFF ID があれば LINE 連携の形)。
- お席の QR から入ったことは、会員登録などで画面を移っても、端末の中(sessionStorage)に4時間だけ覚える。
- お席の QR から入っていなくても、店頭の QR で来店した日は、お席の QR を読み取るボタンを出す。どちらでもない(家など)ときは出さない。ダイニーの店舗IDが空の間は、どの場合も出さない。
- 印刷用のページ `table-qr.html`(入力は端末の中だけ・保存しない)。カードの文言は `TABLE_POP`。

**Web 版の体質チェック(`web-check.html`)**
- SNS・Google ビジネスプロフィール・Web サイトに置く。ログインなし・LINE なしで使える。15問だけ(食事の気分とおすすめの一品は会員証の体質チェックだけ。料理名が仮のため)。
- 判定は画面の中(`evaluate`。DB と同じ判定)。回答はどこにも送らない・保存しないので、同意は求めない(「保存・送信しません」と表示)。計測のタグも入れない。
- 結果の下に、LINE の会員証への登録(会員証の LIFF の URL)・薬日本堂・診断ではない旨。
- 次の段階の候補: ② Web の結果を会員登録のときに引き継ぐ(同意を取ってから記録)、③ 結果のシェア画像、どこから来たかの数(個人を特定しない集計)。

**ダイニーの回答(2026-10-16・小野寺様)で分かったこと**
- 外部のページ(10ZEN の体質チェック)から、各テーブル固定の注文 URL へリンクで進めてよい。テーブルの紐づけ・有効期限・外部からのアクセスの制限はない。LINE ミニアプリ用の URL なら、LINE 会員化・顧客情報の取得も通常どおり。LINE を使わない方も注文できる。追加費用なし(契約予定プランの標準機能)。
- ダイニーの注文画面から体質チェックへ行って戻る機能はない(10ZEN の流れは「体質チェック → 注文」の一方向なので影響なし)。
- 卓上の QR は店舗で用意する。
- 体質チェックの結果は注文画面に反映されない(通常のメニューのまま)。注文のボタンの上に `ORDER_NOTE`(通常のメニューであること・食材やアレルギーはスタッフへ)を出す。
- 導入時に確かめること: LINE ミニアプリ用の注文 URL の正確な形(今の判定は liff.line.me の形だけ)と、テーブルコードの一覧の受け取り方。
