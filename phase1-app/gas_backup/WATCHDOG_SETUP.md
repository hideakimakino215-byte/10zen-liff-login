# バックアップの見張り役 設定手順(本番)

毎日のバックアップが止まったら、自動でメールが届くようにする。人が画面を見に行かなくてよい。

## しくみ

- 見張り役(`watchdog.gs`)は、毎朝9時(日本時間)に「最後に成功したバックアップの時刻」だけを確認する。
- **最後の成功から24時間を超えている**とき、または確認自体ができないときは、通知先へメールを送る。
  - バックアップは毎日3〜4時に動く。正常なら9時の時点で最後の成功は5〜6時間前。
  - その朝のバックアップが失敗すると約29〜30時間前になり、**その朝9時の確認で気づける**(失敗から約5〜6時間後)。
  - 2026-10-14 の監査の指摘を受けて、36時間から24時間に変えた。36時間のままだと、1回の失敗に気づくのが翌々朝(最後の成功から約53時間半後)になっていた。
- 毎月1日には「見張りは動いています」のメールを1通送る。届かない月があれば、見張り役が止まっている。
- 確認の結果は毎回、実行ログに1行残す。**メールが来ないことは、正常に動いた証拠にならない**ため、動いたことは実行ログ(「実行数」の画面)で確かめる。
- 見張り役は、元の秘密(CHECKIN_SECRET)を持たない。持つのは、**時刻の確認にしか使えないよう用途を限定した認証情報**(BACKUP_STATUS_TOKEN)だけ。この認証情報では会員データの書き出し・記録はできない(403)。新しい秘密や有料サービスは増やさない。

## 置き場所と独立性

見張り役は、バックアップ本体とは別の Google プロジェクトに置く。トリガーの削除やプロジェクト単位の故障には、本体と独立して気づける。

- **当面:** 見張り役もバックアップ本体も、牧野さんの Google アカウントにある。**アカウントそのものに障害が起きると、両方が一緒に止まる**(2026-10-14 の監査で暫定として了承)。
- **運営変更のあと:** バックアップ本体を 10ZEN の Google アカウントへ移すとき、**見張り役は同じアカウントに入れない。** 両方を同じアカウントに移しても、この問題は解消しないため。見張り役は別のアカウント(例: 牧野さん個人、本部)に残すか、見張り役が動いていることの確認を別の場所に置く。

## 手順

本番の変更を含む。1 は開発担当(Claude Code)が牧野さんの承認を得て行う。2〜4 は Google にログインした状態で行う(約15分)。

1. **Supabase の backup-export 関数を更新する。** `functions/backup-export` を本番へ反映する。既存の書き出し・記録の動きは変わらない。DB の変更はない。**2026-10-14 反映済み(version 3、牧野さん承認)。**
2. **バックアップ本体の GAS を更新し、トークンを表示する。**
   - バックアップ本体の Apps Script の `backup.gs` の末尾に、`showWatchdogToken` を追加して保存する(2026-10-14 は既存部分を変えず、この関数だけを追加した)。
   - 上の関数の選択から `showWatchdogToken` を選んで実行する。
   - 実行ログに出た64文字の値を控える。
3. **見張り役のプロジェクトを作る。**
   - https://script.google.com で「新しいプロジェクト」を作り、名前を「10ZEN バックアップの見張り」にする。
   - `watchdog.gs` の中身を貼り付けて保存する。
   - 左の歯車(プロジェクトの設定)→ スクリプト プロパティに、次の3つを追加する。

     | プロパティ | 値 |
     |---|---|
     | BACKUP_URL | バックアップ本体と同じ URL(本体のスクリプト プロパティ BACKUP_URL の値) |
     | BACKUP_STATUS_TOKEN | 手順2で控えた64文字 |
     | WATCHDOG_NOTIFY | 通知先のメールアドレス(当面は牧野さん。カンマ区切りで複数可) |

4. **毎朝の実行を設定する。** `installWatchdogTrigger` を実行する。初回は Google の承認画面が出るので許可する。左の時計のアイコン(トリガー)に、`watchdogCheck` が「毎日 午前9時〜10時」で1つ登録されていれば完了。

## 本番での実証(監査の指摘 3)

「翌朝メールが来なかった」だけでは検証にならない。次の3つを、それぞれ記録で確かめる。

| 確かめること | やること | 確かめる記録 |
|---|---|---|
| 更新後の関数で、実際のバックアップ保存と成功記録が通る | バックアップ本体で `dailyBackupNow` を実行する(毎日の処理と同じ。会員データは変えない) | 本番の `backup_runs` に成功の行が増える。Edge Function のログで export・record が 200。ドライブに新しいバックアップのファイル |
| 見張り役が本番の成功時刻を取得できる | 見張り役で `watchdogSelfTest` を実行する(データを変えない) | 実行ログの「見張り役の動作確認」に成功時刻。Edge Function のログで status が 200 |
| 異常時の通知メールが実際に届いて目立つ | 上の `watchdogSelfTest` が試験メールを送る(件名は異常時と同じ付け方) | Gmail に届き、ラベル「10ZEN要対応」・スター・重要が付いている |

あわせて、翌朝9時の自動実行のあと、見張り役の「実行数」の画面で `watchdogCheck` が完了していること、実行ログに確認結果が出ていることを確かめる。

## メールが届いたら

- **「24時間以上止まっています」:** バックアップ本体の Apps Script で `dailyBackupNow` を実行する。エラーになる場合や、トリガーに `dailyBackup` が無い場合は `installBackupTrigger` を実行する。解決しなければ開発担当へ。
- **「状態を確認できません」:** 見張り役の設定(URL・トークン)か、Supabase 側の問題。開発担当へ。
- **「動作確認の試験メール」:** `watchdogSelfTest` を実行したときだけ届く。異常ではない。

## 月次レポート(同じプロジェクトに追加。2026-10-15 実装・本番は未設定)

毎月1日 9時(日本時間)に、前の月の集計をメールで送る(`monthly_report.gs`)。見張り役と同じプロジェクト「10ZEN バックアップの見張り」に、ファイルを1つ足して置く。設計と中身は `REFERRAL_AND_REPORT_DESIGN_20261015.md`。

- **中身:** 4つの KPI(実績・目標・達成率・前の月との差)と新規登録数、会員(新規登録・紹介からの新規来店・ランク別)、体質チェック(タイプ別・今日の体調でいちばん多い答え)、特典チケット(発行・使用・使用率)、注意の行(目標の80%未満・レジの客数が未取り込み)、スタッフ画面のリンク。**集計の数字だけで、氏名・会員番号・LINE ID は含まない。**
- **送らない月:** 本番開始日(スタッフ画面の「目標とKPI」で店長が設定)が未設定の間と、前の月が本番開始日の月より前のとき。開始日の月が終わった次の月の1日から送る。
- **取得できないとき:** 所有者に「月次レポートを作れませんでした」を送る。直ったら `monthlyReport` を実行すると、その月の分を送る(同じ月は1回だけ)。
- **認証情報:** 月次レポートの取得にしか使えないトークン(`REPORT_TOKEN`)。状態の確認・会員データの書き出し・記録には使えない(403)。見張り役のトークンでは月次レポートは取れない。元の秘密(CHECKIN_SECRET)は持たない。トークンは実行ログにもメールにも出さない。

### 本番の設定の手順(牧野さんの承認を得てから)

1. **Supabase に DB の 106 を適用し、backup-export 関数を更新する**(開発担当が承認を得て行う)。`db/106_referral.sql` と `functions/backup-export`。既存の書き出し・記録・状態の確認の動きは変わらない。
2. **バックアップ本体の GAS に `showReportToken` を追加して実行する。** `backup.gs` の末尾の `showReportToken` だけを追加して保存し、実行する。実行ログに出た64文字の値を控える(所有者だけが実行できる。`showWatchdogToken` と同じ形)。
3. **見張り役のプロジェクトに `monthly_report.gs` を追加する。** 「ファイル」の「+」→「スクリプト」で `monthly_report` を作り、中身を貼り付けて保存する。スクリプト プロパティに次を追加する。

   | プロパティ | 値 |
   |---|---|
   | REPORT_TOKEN | 手順2で控えた64文字 |
   | REPORT_TO | 送り先のメールアドレス(当面は牧野さんだけ。店長を足すときはカンマ区切りで追加) |
   | STAFF_URL | スタッフ画面の URL |
   | REPORT_URL(任意) | 省略すると BACKUP_URL(見張り役と同じ backup-export 関数)を使う |

4. **毎月の実行を設定する。** `installMonthlyReportTrigger` を実行する(初回は Google の承認画面が出るので許可する)。トリガーに `monthlyReport` が「月ベース・1日・午前9時〜10時」で1つ登録されていれば完了。
5. **動作確認。** `monthlyReportSelfTest` を実行する。所有者だけに【試験】のメールが届く(本番開始日が未設定なら「送らない月です」の試験メール)。送った記録は残らないので、本番の1日の送信には影響しない。
